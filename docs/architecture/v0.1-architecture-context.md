- **[Confirmed Product Fact]**：正式需求 / CR 已确认的产品事实。
- **[Derived Architecture Requirement]**：由已确认产品事实直接推导出的架构要求。

## 1. System Purpose

### 1.1 产品目的

- **[Confirmed Product Fact]** v0.1 是一个可实际使用的个人记账产品，支持日常收支记录、账户余额管理、按月查询、分类统计和标签统计。
- **[Confirmed Product Fact]** 产品从较小功能范围开始，通过后续 0.x 版本持续演进。
- **[Confirmed Product Fact]** v0.1 面向个人独立使用，不支持家庭共享或多人协作。
- **[Confirmed Product Fact]** 首个客户端为微信小程序；Web、iOS、Android 属于后续版本方向。

### 1.2 v0.1 核心业务闭环

- **[Confirmed Product Fact]** 登录 → 初始化唯一“微信”资金账户及起始余额 → 记录收入 / 支出 → 查看流水、余额与统计 → 必要时通过余额调整修正余额。

### 1.3 本阶段不回答的问题

本文不决定系统最终采用何种应用架构、技术框架、数据库、部署形态或工程结构。

## 3. Architecture Drivers

## 3.1 业务正确性

### 金额与交易语义

- **[Confirmed Product Fact]** 金额最多两位小数；普通交易金额允许正负、不允许为 0。
- **[Confirmed Product Fact]** 收入 / 支出代表业务类型，金额正负代表该业务类型的正向 / 反向结果；系统不得依据金额符号自动改变交易类型。
- **[Derived Architecture Requirement]** 金额表示、计算与聚合必须避免浮点误差，并能稳定支持正负金额语义。

### 余额

- **[Confirmed Product Fact]** 余额 = 起始余额 + 收入金额合计 − 支出金额合计 + 余额调整金额合计。
- **[Confirmed Product Fact]** 所有已保存交易及调整立即影响当前余额，包括未来日期记录。
- **[Derived Architecture Requirement]** 普通交易新增、修改、删除以及余额调整新增、删除必须使当前余额结果保持业务一致。

### 统计

- **[Confirmed Product Fact]** 余额调整不进入收入、支出、分类、标签统计。
- **[Confirmed Product Fact]** 交易按业务时间所属自然月进入月度流水与统计。
- **[Confirmed Product Fact]** 多标签交易完整计入每个标签，但整体收支总计必须按交易去重。
- **[Confirmed Product Fact]** 一级分类汇总与二级分类明细不能重复相加。
- **[Derived Architecture Requirement]** 余额口径、月度收支口径、分类统计口径和标签统计口径必须能够同时成立，不能用一个含义模糊的统一聚合规则替代。

### 编辑与删除

- **[Confirmed Product Fact]** 已保存普通交易类型不可修改。
- **[Confirmed Product Fact]** 已保存余额调整不可编辑，只能删除后重建。
- **[Confirmed Product Fact]** 删除记录必须撤销其原余额影响；普通交易还需撤销统计影响。
- **[Derived Architecture Requirement]** 更新 / 删除路径必须能够可靠地依据原记录语义重新得到正确结果。

---

## 3.2 数据一致性与操作原子性

- **[Confirmed Product Fact]** 保存失败不得留下部分生效数据。
- **[Confirmed Product Fact]** 普通交易保存成功后，交易、余额和相关统计必须保持一致。
- **[Confirmed Product Fact]** 修改 / 删除后余额与统计必须正确变化。
- **[Confirmed Product Fact]** 编辑交易时标签关联变化随交易保存生效；放弃编辑应保留原关联。
- **[Confirmed Product Fact]** 新标签创建是独立行为：标签创建成功后，即使交易随后取消，标签仍然保留。

由此得到：

- **[Derived Architecture Requirement]** 需要明确哪些状态变化必须属于同一个原子操作，哪些状态变化故意具有独立生命周期。
- **[Open Decision]** 普通交易及其标签关联、余额影响、统计结果之间的事务 / 一致性边界如何定义？
- **[Open Decision]** “标签创建独立成功，但交易保存可能失败或取消”的边界如何在领域与应用层表达？
- **[Open Decision]** 余额调整提交时，如果读取当前余额到真正提交之间发生数据变化，如何保持“目标余额 − 提交时当前余额”的既定口径？

本文不选择具体事务实现方式。

---

## 3.3 幂等与重复操作

- **[Confirmed Product Fact]** 一次保存操作不得因重复点击产生多笔交易。
- **[Derived Architecture Requirement]** “防重复”不能只作为视觉反馈要求看待；正式实现需要在可能发生重复请求的边界上有可验证的保证。
- **[Open Decision]** 新增普通交易与余额调整的重复提交识别边界是什么？
- **[Open Decision]** 幂等保证由客户端、服务端、持久化层中的哪些层次共同承担？

本文不决定 request id、幂等键、唯一约束或其他具体方案。

## 3.4 时间语义与稳定排序

### 已确认时间事实

- **[Confirmed Product Fact]** 普通交易与余额调整都有用户选择的业务记录时间，精确到秒。
- **[Confirmed Product Fact]** 默认当前时间；不得早于资金账户创建时间；允许未来时间。
- **[Confirmed Product Fact]** 业务记录时间决定自然月归属和流水主排序，不决定是否影响当前余额。
- **[Confirmed Product Fact]** 业务月份与时间展示使用北京时间。
- **[Confirmed Product Fact]** 同一业务秒内，后保存记录排在前面。
- **[Confirmed Product Fact]** 同秒排序依据使用首次保存先后；普通编辑不得改变该依据。

### 架构要求与开放问题

- **[Derived Architecture Requirement]** 正式数据模型必须区分“用户指定的业务时间”与“首次保存顺序 / 首次保存时点”的语义，不能用一个时间字段同时承担两个含义。
- **[Derived Architecture Requirement]** 编辑时间（如正式实现需要）不能替代首次保存排序依据。
- **[Open Decision]** 正式实现中需要哪些时间语义以及如何表示北京时间业务边界？
- **[Open Decision]** 如何实现同秒情况下绝对稳定、可重复的排序兜底？
- **[Unknown / Not Defined]** 除业务时间和首次保存排序语义外，产品资料没有要求审计级时间线或完整历史版本记录。

本文不设计具体数据库字段。

## 3.5 数据隔离

- **[Confirmed Product Fact]** 资金账户、交易、分类和标签均归属于用户。
- **[Confirmed Product Fact]** 用户只能查看和操作自己的数据；不能仅依赖页面隐藏。
- **[Confirmed Product Fact]** 不同用户可以存在同名分类和标签（在各自用户范围内遵循唯一性规则）。
- **[Derived Architecture Requirement]** 数据归属与访问控制必须在可信服务边界中执行，而不是只由客户端过滤。
- **[Open Decision]** 用户上下文如何贯穿身份认证、业务操作、查询与持久化边界？
- **[Open Decision]** 数据唯一性约束如何与用户隔离语义协同？

## 3.6 安全

- **[Confirmed Product Fact]** v0.1 使用预先创建的用户名密码账号。
- **[Confirmed Product Fact]** 登录密码不得明文保存。
- **[Derived Architecture Requirement]** 正式实现需要安全保存密码，并在可信服务边界完成身份校验。
- **[Open Decision]** v0.1 的认证机制、会话 / 凭证生命周期与退出语义如何实现？
- **[Unknown / Not Defined]** 产品资料没有定义密码复杂度、登录失败锁定、MFA、验证码、安全审计、传输加密细节或其他账户安全策略。

---

## 3.7 持久化、恢复与可靠性

- **[Confirmed Product Fact]** 数据在退出、应用重启、重新登录后必须仍然存在。
- **[Confirmed Product Fact]** 使用真实数据前必须具备可执行的备份及恢复办法。
- **[Derived Architecture Requirement]** 正式系统需要持久化存储，而原型 `localStorage` 不具备正式数据存储含义。
- **[Derived Architecture Requirement]** 备份与恢复必须在真实数据使用前至少形成可执行路径，并能够覆盖业务所依赖的持久化状态。
- **[Open Decision]** 正式持久化技术采用什么类型与产品？
- **[Open Decision]** v0.1 最小可接受的备份、恢复和验证方式是什么？
- **[Unknown / Not Defined]** 现有资料没有规定 RPO、RTO、备份频率、备份保存周期、跨区域灾备或高可用等级。

## 3.8 可演进性

- **[Confirmed Product Fact]** 已知未来方向包括多资金账户与转账、分类 / 标签管理、待确认交易、更多登录方式、家庭共享、更多客户端、投资资产、图表及 AI 能力。

- **[Open Decision]** 哪些 v0.1 边界需要留出低成本演进点，哪些可以等真实需求出现后重构？

## 6. 架构开放问题

以下问题进入后续 Domain Modeling / Architecture Decision 阶段讨论。本节只描述问题及其来源，不给答案。

### 6.1 余额是计算结果还是持久化状态？

- **来源**：余额由起始余额、全部普通交易和余额调整共同定义；新增 / 修改 / 删除都必须保持正确。
- **[Open Decision]** 当前余额应按记录实时计算、维护为持久化状态，还是采用其他可验证方式？
- **关注点**：正确性、一致性、查询成本、修改 / 删除语义、并发情况下的余额调整。

### 6.2 Transaction 与 BalanceAdjustment 如何建模？

- **来源**：二者都显示在流水、都影响余额，但余额调整没有普通收支类型、分类和标签，也不进入收支统计，且编辑规则不同。
- **[Open Decision]** 它们应属于同一领域抽象的不同记录类型，还是两个独立领域对象 / 聚合？
- **关注点**：共同能力、不同不变量、查询统一性、统计隔离、未来演进。

### 6.3 月度统计如何得到？

- **来源**：需要月度总计、分类统计、标签统计；多标签存在重复覆盖，一级 / 二级分类不能重复相加。
- **[Open Decision]** 统计采用实时查询聚合、维护汇总状态，还是其他方式？
- **关注点**：正确性、复杂度、数据规模未知、修改 / 删除一致性。

### 6.4 写操作的事务边界是什么？

- **来源**：保存失败不能部分生效；标签创建又被明确设计为可独立成功。
- **[Open Decision]** 普通交易、标签关联、余额影响等哪些变化必须原子提交？标签独立创建如何与交易保存边界共存？

### 6.5 重复提交如何保证不重复创建？

- **来源**：正式质量要求明确重复点击不能产生重复记录。
- **[Open Decision]** 正式系统采用什么重复识别语义和技术保障？

### 6.6 身份认证与用户上下文如何实现？

- **来源**：用户名密码登录、退出、密码不得明文、所有业务数据按用户隔离。
- **[Open Decision]** 认证、凭证 / 会话、用户上下文、授权边界如何设计？

### 6.7 正式持久化采用什么？

- **来源**：数据需长期持久保存、支持一致性写入、用户隔离和备份恢复。
- **[Open Decision]** 选择何种持久化类型 / 数据库产品最适合 v0.1？

### 6.8 时间字段与排序机制如何建模？

- **来源**：业务时间与首次保存排序语义不同；同秒需要稳定排序；编辑不得改变首次保存排序依据。
- **[Open Decision]** 时间、首次保存顺序以及可选的更新时间如何表达？如何确保排序稳定且可重复？

### 6.9 余额调整提交时的并发语义如何保障？

- **来源**：差额必须按提交时当前余额计算；CR-002 已将并发实现留到架构阶段。
- **[Open Decision]** 如果从打开页面到提交期间余额发生变化，正式实现怎样保证使用提交时当前余额并避免错误差额？

### 6.10 备份恢复的最小可执行方案是什么？

- **来源**：真实数据使用前必须有可执行备份恢复办法。
- **[Open Decision]** v0.1 的最小备份单位、频率、恢复步骤与验证方式是什么？

### 6.11 系统整体需要什么复杂度？

- **来源**：当前业务范围较小，但存在未来演进方向；性能规模、部署要求、团队规模均未在产品资料定义。
- **[Open Decision]** 在满足正确性、可靠性和可维护性的前提下，v0.1 应采用多简单的总体架构？
- **关注点**：避免“为了未来”引入没有当前驱动因素的复杂组件。

## 7. Over-engineering Risks

以下区域是后续由 AI 或开发人员进行设计时最容易提前扩大范围的地方。

### 7.1 因未来多账户而提前实现复杂账户 / 转账平台

- **风险**：v0.1 每用户只有一个固定“微信”账户，转账明确 Out of Scope。
- **提醒**：可以避免把当前设计彻底封死，但不应实现尚不存在的转账状态机、账户体系或跨账户一致性能力。

### 7.2 因未来家庭共享而提前建设 RBAC / ACL

- **风险**：当前只要求用户数据隔离，不要求家庭共享和角色权限。
- **提醒**：需要可信的用户归属检查，但不能据此推导出复杂权限平台。

### 7.3 为小范围 v0.1 引入微服务

- **风险**：当前没有独立团队、独立扩容、服务隔离、超大规模等产品驱动信息。
- **提醒**：是否采用微服务属于架构方案阶段问题，目前不存在产品事实要求它。

### 7.4 在无规模指标时提前引入 Redis / MQ / 分布式锁

- **风险**：性能与并发规模均未定义。
- **提醒**：这些技术只能由明确的一致性、性能或运行需求驱动，不能因“常见架构组件”而默认加入。

### 7.5 为统计提前建设复杂汇总 / OLAP 系统

- **风险**：当前统计维度有限，数据规模未知，且正确性优先。
- **提醒**：先在下一阶段比较简单聚合与维护汇总的真实成本，不提前建立复杂分析体系。

### 7.6 为未来更多客户端提前建设过度通用的平台层

- **风险**：当前正式客户端仅微信小程序。
- **提醒**：接口与领域语义可以避免强绑定 UI，但不需要提前实现跨端平台产品。

### 7.7 为未来 AI 记账提前引入 AI 基础设施

- **风险**：AI 记账明确不在 v0.1 范围。
- **提醒**：当前项目“使用 AI 开发”与产品“内置 AI 能力”是两回事。

### 7.8 把原型实现细节误认为正式架构

- **风险**：原型使用单文件 HTML、浏览器 `localStorage`、原生 `datetime-local`、演示工具和递增模拟序号。
- **提醒**：这些只是交互验证实现，不具有正式技术方案约束力。

## 9. Architecture Context 阶段结论

### 9.1 已经明确

- v0.1 的业务范围与边界已经冻结；
- 正确性、一致性、时间、用户隔离、密码安全、持久化、幂等和备份恢复是明确的架构驱动因素；
- 多账户、家庭共享、投资资产、复杂图表、AI 产品能力等不属于当前实现范围；
- 当前产品资料没有给出高并发、高可用或分布式系统方面的驱动信息；
- Java / Spring Boot / MySQL 等技术选择尚未由本阶段正式决定。

### 9.2 当前是否存在阻塞进入下一阶段的问题

**未发现阻塞进入 Domain Modeling 的产品问题。**

跨月份保存后的列表定位属于 Open UX Decision，但不影响核心业务语义和领域边界。

### 9.3 下一阶段建议输入

下一阶段进入 **Domain Modeling** 时，优先围绕以下问题建模，而不是从数据库表出发：

- User、Account、Transaction、Category、Tag、BalanceAdjustment 的业务身份与关系；
- 各对象必须始终成立的不变量；
- 普通交易与余额调整的共同点和差异；
- Balance 的业务本质；
- 标签创建与交易保存的生命周期边界；
- 业务时间与首次保存顺序的领域语义；
- 新增、修改、删除时哪些业务变化构成一个一致性边界。

这些问题在下一阶段讨论；本文不预先给出模型答案。
