# 1. Executive Summary / 推荐方案总体轮廓

在当前 v0.1 已知条件下，推荐轮廓为：

```text
WeChat Mini Program / 微信小程序
            │
            │ HTTPS + authenticated request
            ▼
Modular Monolith Backend / 模块化单体后端
Java + Spring Boot
            │
            │ single relational transaction boundary
            ▼
PostgreSQL（推荐）
            │
            ├── Transaction source facts
            ├── BalanceAdjustment source facts
            ├── Category / Tag / associations
            └── User / Account / session state

Balance            = query-time derived value
Monthly Statistics = query-time derived read model
Ledger              = Transaction + BalanceAdjustment read composition
```

核心技术原则：

1. **单一后端部署单元，不采用微服务。**
2. **领域内部保持模块边界，但不引入复杂模块化框架。**
3. **关系型数据库作为持久化真相来源。**
4. **Balance 与 Statistics 在 v0.1 优先实时派生，不提前维护冗余汇总状态。**
5. **Transaction 与 BalanceAdjustment 分开持久化，但 Ledger 查询统一组合。**
6. **所有影响账户余额的写操作通过同一个 Account 级串行化边界协调。**
7. **CreateTransaction / CreateBalanceAdjustment 使用服务端可验证的幂等机制，不能只靠前端防重复。**
8. **业务时间、首次保存系统时间、首次保存顺序、更新时间四种语义分开。**
9. **认证优先使用随机 Opaque Token + 服务端 Session，而不是为 v0.1 引入 JWT 体系。**
10. **不引入 Redis、MQ、Kafka、Elasticsearch、Kubernetes、CQRS、Event Sourcing。**

# 2. Architecture Evaluation Principles / 评价原则

以下优先级用于所有方案比较：

1. Business Correctness / 业务正确性；
2. Consistency / 一致性；
3. Data Security / 数据安全；
4. 与已确认 Domain Model 的一致性；
5. Simplicity / 简单性；
6. Testability / 可测试性；
7. Maintainability / 可维护性；
8. 单人 + AI Coding Agent 的开发效率；
9. 运维成本；
10. 合理演进空间。

当前没有高并发、高可用、跨区域、多团队独立部署等 Architecture Driver，因此不以“理论最大扩展性”为优先目标。

# 3. A. Overall Application Architecture / 总体应用架构

## Option A1：Simple Monolith / 简单单体

一个后端应用，在代码内部主要按常规分层组织，不特别强调领域模块边界。

### 优点

- 最简单；
- 开发速度快；
- 一个进程、一套事务、一套部署；
- 当前规模完全可以承载。

### 缺点

- 如果 AI Coding 持续扩展功能，代码容易逐渐按技术层横向堆积；
- Account、Transaction、Statistics、Authentication 等业务边界容易互相穿透；
- v0.2 以后功能增加时维护成本上升。

### 过度设计风险

低。

---

## Option A2：Modular Monolith / 模块化单体

仍然是一个后端应用和一个部署单元，但在代码层显式保持业务模块边界。

例如概念上可以存在：

- identity / 用户身份；
- account / 账户；
- transaction / 普通交易；
- tag-category / 分类标签；
- ledger-statistics / 查询统计。

这里仅表示架构边界，不是本轮确定 Java 包结构。

### 优点

- 保留单体的简单部署和本地事务优势；
- 对 AI Coding Agent 更容易限定 Context 和修改范围；
- 有利于 v0.2 以后增量演进；
- 不需要付出微服务通信、部署、可观测性等成本。

### 缺点

- 需要主动维护模块边界；
- 如果过度追求“模块纯洁”，也可能增加不必要抽象。

### 过度设计风险

低，只要不引入复杂模块框架或强制 DDD 基础设施。

---

## Option A3：Microservices / 微服务

拆成用户、账户、交易、统计等独立服务。

### 优点

- 理论上可以独立部署和扩缩容；
- 未来大团队可形成独立服务责任边界。

### 缺点

- 当前没有独立团队、独立扩容或高并发驱动；
- 交易、余额调整和统计存在一致性关系，拆服务会把本地事务问题升级为分布式一致性问题；
- 增加网关、服务发现、部署、日志追踪、故障处理等成本；
- 对单人 + AI 项目属于明显复杂化。

### 过度设计风险

**极高。**

### Recommended

**A2：Modular Monolith。**

推荐理由：保留单体事务和部署简单性，同时通过轻量模块边界降低 AI 长期生成代码造成的耦合风险。

**Confidence：High**  
**Needs Human Review：No**

---

# 4. B. Client / Server Boundary / 客户端与服务端边界

## Option B1：WeChat Mini Program + Independent Backend / 微信小程序 + 独立后端

小程序只承担交互和客户端状态，核心业务规则、认证、用户隔离、持久化在可信后端执行。

### 优点

- 用户隔离和核心业务规则有可信执行边界；
- 与关系型事务、备份恢复天然匹配；
- 后续 Web / iOS / Android 可以复用业务后端；
- 技术和数据可迁移性较好；
- 本地开发、测试和 AI Coding 路径清晰。

### 缺点

- 需要维护后端运行环境；
- 需要独立解决数据库、日志、备份和部署。

---

## Option B2：Cloud Functions / Serverless / 云函数

业务通过云函数承载，数据库使用平台能力。

### 优点

- 初始服务器运维工作少；
- 小流量情况下按量付费可能简单；
- 与部分小程序云平台集成方便。

### 缺点

- 平台绑定程度更高；
- 本项目有较明确的关系型事务与 Account 级一致性需求，函数边界并不能带来明显收益；
- 本地测试、数据库事务、一致性锁、备份恢复能力依赖具体平台；
- 后续更多客户端时平台耦合可能增加迁移成本。

### 过度设计风险

不属于过度设计，但会把部分技术决策交给云平台约束。

### Recommended

**B1：微信小程序 + 独立后端。**

不是因为“传统架构更标准”，而是当前产品要求持久化、可信用户隔离、密码认证、事务一致性、备份恢复，并已明确更多客户端是未来方向；独立后端使这些规则集中在稳定边界中。

如果后续部署成本或平台约束发生明显变化，可以重新评估 Serverless。

**Confidence：Medium-High**  
**Needs Human Review：Yes**（主要取决于后续实际部署平台与运维偏好）

# 5. C. Backend Technology Stack / 后端技术栈

## Option C1：Java + Spring Boot

### 优点

- 强类型模型与当前 Domain Model 匹配；
- 成熟的事务、安全、测试、数据库生态；
- 对领域不变量和事务边界表达清楚；
- AI Coding 对 Spring 生态支持成熟；
- 项目开发者已有深厚 Java 企业应用经验，可以把精力放在 AI 协作和架构质量，而不是学习语言基础。

### 缺点

- 对极小 Demo 而言启动和工程结构比脚本语言略重；
- 如果只追求几十个接口的最快实现，Node.js 可更轻。

---

## Option C2：Node.js + TypeScript

### 优点

- TypeScript 也具备较好类型约束；
- 小项目启动快；
- AI 代码生成生态良好；
- 前后端语言统一。

### 缺点

- 当前没有前后端统一语言的实际团队收益；
- 需要重新建立事务、安全、工程约束的实践习惯；
- 对当前学习目标没有明显架构收益足以抵消切换成本。

---

## Option C3：其他语言

当前不存在明确 Architecture Driver 要求 Go、Python、Kotlin 等其他技术，不为了方案数量额外展开。

### Recommended

**C1：Java + Spring Boot。**

推荐不仅基于熟悉程度，也因为该项目的核心难点是关系型事务、领域约束、认证和长期维护，不是高吞吐或极简函数执行。Java/Spring Boot 对这些要求没有结构性短板。

**Confidence：High**  
**Needs Human Review：No**

# 6. D. Persistence / 持久化

## Option D1：PostgreSQL

### 优点

- 完整关系型事务与约束能力；
- 适合 Transaction、Tag Association、Category 层级等关系模型；
- 聚合统计、复杂查询能力成熟；
- 备份恢复工具成熟；
- **数据库 Sequence 可以为分开的 Transaction 与 BalanceAdjustment 提供共享、单调递增的 First Save Order，直接满足跨两类流水的稳定同秒排序要求。**

### 缺点

- 如果最终部署环境只提供更便宜或更成熟的 MySQL 托管能力，会增加运维选择成本；
- 团队需要遵循 PostgreSQL 的具体运维和 SQL 习惯。

---

## Option D2：MySQL

### 优点

- 成熟、稳定、生态广；
- 事务、关系查询、备份恢复均能满足当前业务；
- 开发者熟悉；
- 多数托管平台支持良好。

### 缺点

- Transaction 与 BalanceAdjustment 若分表，各自 AUTO_INCREMENT 无法天然表达两张表之间的统一 First Save Order；
- 需要额外设计共享排序号分配机制，例如独立排序号分配记录或应用层生成机制；
- 这不是不能解决，但会多一个技术机制。

---

## Option D3：SQLite

### 优点

- 极简部署；
- 备份文件直观；
- 对纯单机个人应用非常合适。

### 缺点

- 当前首个客户端是微信小程序，推荐架构是独立后端；
- 多请求并发写、远程部署、备份运维和未来更多客户端下，不如服务型关系数据库自然；
- 为减少一个数据库服务而承担未来迁移成本，收益有限。

### Recommended

**D1：PostgreSQL。**

MySQL 同样能够正确实现 v0.1，二者不是能力等级差异。PostgreSQL 在本项目里有一个具体优势：如果 Transaction 与 BalanceAdjustment 分开持久化，数据库原生 Sequence 可以非常低成本地生成跨两类记录统一的 First Save Order。

如果最终部署环境对 MySQL 有明显成本、运维或平台优势，选择 MySQL 仍然合理，但需要显式解决共享保存顺序。

**Confidence：Medium**  
**Needs Human Review：Yes**

# 7. E. Balance Technical Strategy / Balance 技术策略

领域基线：Balance 是 Derived Value，源事实是 Opening Balance + Transaction + BalanceAdjustment。

## Option E1：Query-time Aggregation / 每次实时聚合

每次需要 Current Balance 时，根据源事实计算。

### 优点

- 单一真相来源；
- 新增、编辑、删除不需要同步维护额外余额状态；
- 出现问题时可直接从源记录重算；
- 与领域模型最一致。

### 缺点

- 查询会扫描 / 聚合相关记录；
- 数据量很大时需要优化。

---

## Option E2：Persisted Current Balance / Account 冗余当前余额

每次余额相关写操作同时修改 Account Current Balance。

### 优点

- 读取极快；
- 创建余额调整时容易读取当前状态。

### 缺点

- Transaction 修改 / 删除必须维护冗余值；
- 容易出现源记录与冗余余额不一致；
- 需要补偿 / 校验 / 重算机制；
- 当前个人数据规模没有性能驱动。

---

## Option E3：Hybrid / 混合

源事实仍为真相来源，同时维护可重建缓存或冗余余额。

### 优点

- 性能和可恢复性兼顾。

### 缺点

- 当前会增加额外一致性和测试成本；
- 在没有性能问题前属于提前优化。

### Recommended

**E1：v0.1 采用 Query-time Aggregation。**

Current Balance 每次从源事实计算。未来如真实数据规模出现性能问题，可增加“可重建的派生缓存 / 冗余余额”，但不改变源事实地位。

**Confidence：High**  
**Needs Human Review：No**

---

# 8. F. Statistics Strategy / 统计技术策略

## Option F1：Query-time SQL Aggregation / 查询时实时聚合

### 优点

- 与 Derived Read Model 完全一致；
- Transaction 修改和删除后天然反映最新结果；
- 没有汇总状态同步问题；
- v0.1 数据规模小。

### 缺点

- 未来数据量大时查询成本增加。

---

## Option F2：Summary Tables / 汇总表

### 优点

- 查询快。

### 缺点

- 修改交易月份、金额、分类、Tag 时要同步多套汇总；
- 多标签完整重复计入使维护逻辑更复杂；
- 当前无性能驱动。

---

## Option F3：Cache / Async Statistics / 缓存或异步统计

### 优点

- 适合高流量读取和大数据量。

### 缺点

- 引入缓存失效、异步最终一致性或消息机制；
- 与当前“正确性优先”的 v0.1 不匹配。

### Recommended

**F1：查询时实时聚合。**

需要通过合理索引和查询设计保证当前规模性能；是否建立汇总或缓存等到真实性能证据出现后再决定。

**Confidence：High**  
**Needs Human Review：No**

# 9. G. Transaction / BalanceAdjustment Persistence Shape

## Option G1：Separate Persistence Structures / 分开持久化

Transaction 与 BalanceAdjustment 分开保存，在 Ledger 查询中组合。

### 优点

- 与领域模型完全一致；
- 各自字段与约束清晰；
- 不产生大量无意义空字段；
- 更容易保证 BalanceAdjustment 没有 Category / Tag、Transaction 必须有 Category 等规则。

### 缺点

- Ledger 需要组合两类来源；
- First Save Order 必须跨两类记录统一生成。

---

## Option G2：Single Unified Record / 单一统一表 + 类型区分

### 优点

- Ledger 查询和统一排序直接；
- 一个统一自增顺序容易得到。

### 缺点

- 为不同领域对象制造大量可空字段；
- 数据库约束更难表达；
- 领域差异被表结构弱化；
- 容易让持久化设计反向污染领域设计。

### Recommended

**G1：分开持久化。**

Ledger 统一查询的问题应在 Read Model 解决，不应为了列表查询方便而把两个独立领域对象强行合表。

**Confidence：High**  
**Needs Human Review：No**

# 10. H. Transaction Boundary / 事务边界

## CreateTransaction

推荐一个关系型数据库事务中完成：

- 验证 Account / Category / Tag 的归属和合法性；
- 创建 Transaction；
- 创建最终 Transaction-Tag Association Set；
- 分配不可变 First Save Order；
- 整体成功或失败。

已提前独立创建的 Tag **不包含在该事务回滚范围中**。

## EditTransaction

一个事务中完成：

- 锁定 / 校验目标 Transaction；
- 保持 Transaction Type 和 First Save Order 不变；
- 更新可编辑字段；
- 替换最终 Category / Tag Associations；
- 整体成功或保持原状态。

## DeleteTransaction

一个事务中完成 Transaction 及其 Associations 的失效 / 删除。

## CreateBalanceAdjustment

一个事务中完成：

- 获得 Account 的并发协调权；
- 计算提交时 Current Balance；
- 计算 Adjustment Amount；
- 若差额非零则创建 BalanceAdjustment 并分配 First Save Order；
- 整体提交。

## DeleteBalanceAdjustment

一个事务中完成删除，并与其他影响同一 Account 的写操作使用同一并发协调规则。

### Recommended

全部核心写操作使用**单一关系型数据库本地事务**，不引入分布式事务。

**Confidence：High**  
**Needs Human Review：No**

# 11. I. Idempotency / 幂等

## Option I1：Frontend Guard Only / 只靠前端禁止重复点击

### 优点

- 简单。

### 缺点

- 网络超时后重试、客户端重复请求、用户快速点击仍可能绕过；
- 无法满足服务端可验证的“不重复创建”保证。

不推荐作为唯一机制。

---

## Option I2：Client Operation ID + Server / DB Uniqueness

创建操作由客户端生成一次性 Operation ID / Idempotency Key；同一保存意图重试时复用同一个 Key。

服务端持久化并以唯一约束保证相同 Key 只产生一次业务结果。

### 优点

- 网络重试安全；
- 机制清晰；
- 不需要 Redis；
- 与数据库事务配合容易验证。

### 缺点

- 客户端需要管理一次保存意图的 Key 生命周期；
- 服务端需要定义重复请求返回已有结果的语义。

---

## Option I3：Redis / Distributed Idempotency

当前没有多实例、高并发驱动，引入 Redis 只为防重复属于过度设计。

### Recommended

采用：

1. 前端保存按钮短时禁用，作为 UX 防护；
2. **CreateTransaction / CreateBalanceAdjustment 等创建型操作使用 Operation ID / Idempotency Key；**
3. 服务端 + 数据库唯一约束作为最终保证。

更新 / 删除针对已存在资源，本身按照资源身份和事务规则处理，不为所有请求统一建设复杂幂等平台。

**Confidence：High**  
**Needs Human Review：No**

---

# 12. J. BalanceAdjustment Concurrency / 余额调整并发

业务要求：

```text
Adjustment Amount = Target Balance - Current Balance at Commit
```

关键不只是 BalanceAdjustment 自身并发，而是**任何会改变 Account Balance 的 Transaction / Adjustment 写操作都可能与它竞争。**

## Option J1：Account-level Pessimistic Lock / Account 行级悲观锁

所有影响同一 Account Balance 的写操作，在事务开始阶段获得同一个 Account 级数据库锁。

CreateBalanceAdjustment 获取锁后再实时聚合 Current Balance 并计算差额。

### 优点

- 业务语义直观；
- 低并发个人账户场景下锁竞争极低；
- 不需要额外分布式锁；
- 与实时 Balance 聚合方案匹配。

### 缺点

- 所有余额相关写操作必须遵守同一锁协议；
- 如果未来单账户高并发，会降低并行写能力。

---

## Option J2：Optimistic Version / 乐观版本

Account 保存 version，所有影响 Balance 的写操作更新 version；BalanceAdjustment 提交时检查 version，冲突则重算 / 重试。

### 优点

- 读写并行度高；
- 冲突少时成本低。

### 缺点

- 在 Balance 本身不持久化时，需要额外维护 version 作为协调状态；
- 所有余额相关写路径必须正确触发版本变化；
- 实现和重试语义比当前需求更复杂。

---

## Option J3：Serializable Isolation / 全局更强隔离级别

### 优点

- 理论语义强。

### 缺点

- 对全部事务提升隔离成本；
- 冲突处理和数据库行为更复杂；
- 当前没有必要。

### Recommended

**J1：Account-level database row lock。**

所有会改变 Account Balance 的 Create/Edit/Delete Transaction、Create/Delete BalanceAdjustment 在事务内遵守相同 Account 锁协议。CreateBalanceAdjustment 获得锁之后再计算 Current Balance。

这是数据库本地锁，不引入 Redis / distributed lock。

**Confidence：High**  
**Needs Human Review：No**

---

# 13. K. Time and Ordering / 时间与排序

领域规则：

```text
Business Record Time DESC
First Save Order DESC
```

并明确：

- Business Record Time 是用户选择的业务发生时间；
- First Saved Time 是第一次成功进入系统的系统时点；
- First Save Order 是不可变的跨流水保存顺序；
- Updated Time 只是可选 Technical Metadata。

## Option K1：只使用高精度 First Saved Timestamp 作为次排序

### 优点

- 字段少。

### 缺点

- 高精度 timestamp 仍不能在所有并发 / 数据库环境下数学上保证绝不并列；
- CR-002 已明确不能只靠“更高时间精度”作为最终稳定排序保证。

不推荐。

---

## Option K2：Global Monotonic First Save Order / 全局单调保存顺序

每条 Transaction 和 BalanceAdjustment 首次保存时获得一个跨两类记录共享的不可变单调序号。

同时记录 First Saved Time 作为系统时间元数据。

### 优点

- 严格满足同秒排序；
- 编辑不改变顺序；
- Ledger 两种记录可以稳定组合；
- 语义与领域模型直接对应。

### 缺点

- 数据库 / 应用需要提供跨两类记录的统一序号发生机制；
- 如果选择 MySQL + 分表，需要额外排序号分配机制。

### Recommended

采用 **K2**：

- Business Record Time：保存用户填写的北京时间业务时间语义；不能依赖服务器默认时区；
- First Saved Time：系统生成的实际首次保存时间；
- First Save Order：数据库侧共享单调序号；
- Updated Time：技术元数据，不参与业务排序。

如果采用 PostgreSQL，推荐使用数据库 Sequence 生成跨 Transaction / BalanceAdjustment 的共享 First Save Order。

**Confidence：High（排序模型） / Medium（具体生成机制取决于数据库）**  
**Needs Human Review：Yes**

---

# 14. L. Authentication / 认证

## Option L1：Cookie / Server Session

传统服务器 Session，通过 Cookie 标识。

### 优点

- 服务端可直接失效；
- 语义简单。

### 缺点

- 微信小程序不是传统浏览器页面，Cookie 并不是最自然的客户端凭证表达；
- 跨未来客户端时需要适配。

---

## Option L2：JWT Access Token

### 优点

- 客户端使用 Authorization Header 自然；
- 无需每次读取服务端 Session 状态。

### 缺点

- v0.1 没有大规模分布式认证需求；
- Logout / 主动失效 / 密钥轮换等语义会变复杂；
- 容易为了“无状态”引入多余 token 生命周期设计。

---

## Option L3：Opaque Token + Server-side Session

登录成功后生成高熵随机 Token；客户端放在 Authorization Header；服务端根据 Token 获取 Session 与 User Context。

Session 状态可存关系数据库，v0.1 不引入 Redis。

### 优点

- 对小程序和未来 App 客户端自然；
- Logout 可以直接使 Session 失效；
- 服务端掌握凭证生命周期；
- 不需要 JWT 撤销机制；
- 单实例 / 低流量读取数据库 Session 成本可忽略。

### 缺点

- 每次认证需要查询服务端 Session 状态；
- 多实例高流量时以后可能需要缓存，但当前没有该驱动。

### Password Storage

无论采用哪种 Session 方式，密码必须使用成熟的自适应单向密码哈希方案，绝不明文或可逆加密保存。

### Recommended

**L3：Opaque Token + DB-backed Server Session。**

不引入完整 IAM，不引入 Refresh Token / JWT 体系，除非未来认证场景扩大。

**Confidence：Medium-High**  
**Needs Human Review：Yes**

---

# 15. M. User Data Isolation / 用户数据隔离

## Option M1：Client passes User ID / 客户端传用户 ID 后过滤

不可信。不能满足正式需求。

---

## Option M2：Authenticated User Context + Server-side Ownership Scope

认证成功后由服务端从 Session 得到可信 `User Context`。

所有 Command / Query 均在 User Context 中执行：

- 不信任客户端传入的 User ID；
- Account / Transaction / Tag / Category 查询必须限制 Owner；
- 修改和删除同时验证资源归属；
- 数据库唯一性约束把 User Scope 纳入语义，例如 Tag Name 的用户级唯一性；
- 不建设 RBAC / ACL，因为当前只有“本人数据”这一权限模型。

### Recommended

**M2。**

**Confidence：High**  
**Needs Human Review：No**

# 16. N. Backup & Restore / 备份恢复

## Option N1：Only Managed Snapshot / 只依赖云数据库快照

### 优点

- 运维简单。

### 缺点

- 恢复流程依赖供应商；
- 用户要求的是“可执行备份与恢复办法”，不能只知道平台“有备份”；
- 不利于数据迁移和恢复演练。

---

## Option N2：Logical Backup + Restore Script + Restore Drill

定期导出逻辑备份；备份文件保存在与数据库故障域不同的位置；提供可执行恢复步骤，并周期性做恢复验证。

### 优点

- 数据量小，执行成本低；
- 数据可迁移；
- 真正验证“可以恢复”；
- 不依赖复杂灾备系统。

### 缺点

- 需要维护备份任务和保留策略；
- 恢复验证需要额外操作。

---

## Option N3：Enterprise HA / Cross-region Disaster Recovery

当前没有 RPO/RTO、SLA、跨区域要求，明显过度设计。

### Recommended

**N2 为基线，N1 可作为额外保障。**

v0.1 在投入真实数据前至少需要：

- 自动或固定周期的逻辑备份；
- 与主数据库独立保存的备份副本；
- 明确恢复命令 / 脚本；
- 至少一次完整恢复演练；
- 后续周期性抽查恢复可用性。

具体备份频率和保留时间由于产品没有 RPO/RTO，本轮不强行拍板。

**Confidence：High**  
**Needs Human Review：No（频率 / 保存位置在部署阶段确认）**

# 19. Cross-cutting Recommendation / 跨决策组合验证

单项推荐组合后，需要检查是否相互兼容。

推荐组合：

```text
Modular Monolith
+ Java / Spring Boot
+ Independent Backend
+ PostgreSQL
+ Separate Transaction / BalanceAdjustment persistence
+ Query-time Balance
+ Query-time Statistics
+ DB local transactions
+ Account-level row lock for balance-changing writes
+ Idempotency Key + DB uniqueness
+ Global First Save Order sequence
+ Opaque Token + DB-backed Session
+ User-scoped access
+ Logical backup + restore drill
+ Minimal logging + health check
+ Single-instance deployment
```

### 一致性检查

**Balance 与并发：兼容。**  
Balance 虽实时计算，但 BalanceAdjustment 创建前通过 Account lock 与其他余额写操作串行，确保“提交时余额”语义。

**Transaction / BalanceAdjustment 分开与流水排序：兼容。**  
通过共享 First Save Order 解决分表后跨类型同秒排序。

**PostgreSQL 与共享顺序：匹配。**  
Sequence 可作为独立于具体业务表 ID 的共享排序号来源。

**实时统计与事务：兼容。**  
统计不维护独立写状态，因此 Transaction 写入成功后查询自动反映新结果，不需要同步消息。

**Opaque Session 与单实例：兼容。**  
Session 存数据库，不依赖进程内内存，因此未来增加第二个实例时也不必先迁移 Session 语义。

**模块化单体与数据库本地事务：兼容。**  
业务模块可保持边界，同时需要强一致的写操作仍在同一数据库事务中完成。

# 22. Decisions Most Worth Human Review / 最值得人工 Review 的问题

## 22.1 PostgreSQL vs MySQL

这是当前最具体的技术选型 Review 点。

两者都能正确实现产品。推荐 PostgreSQL 的主要额外理由不是“数据库更先进”，而是：

> **当前 Domain Baseline 要求 Transaction 与 BalanceAdjustment 独立，同时 Ledger 同秒必须跨两类记录保持严格首次保存顺序；PostgreSQL 共享 Sequence 能非常直接地解决这个问题。**

如果部署、成本或组织环境明显偏向 MySQL，那么应该接受 MySQL，并单独设计共享 First Save Order 机制，而不是为了排序规则强制换数据库。

---

## 22.2 Independent Backend vs Serverless

这主要不是代码问题，而是长期运行形态选择。

当前推荐独立后端，因为业务规则、认证、事务和未来多客户端都更自然；如果后续实际托管环境显示 Serverless 显著降低个人运维成本，则值得重新评估。

---

## 22.3 Ordering Implementation

领域排序已经冻结，值得 Review 的不是业务规则，而是：

> 是否接受“跨 Transaction / BalanceAdjustment 的数据库共享序号”作为 First Save Order 技术实现。

这是一个小但长期稳定的基础设计，一旦进入数据库模型后会被大量查询依赖。

---

## 22.4 Authentication

推荐 Opaque Token + DB Session，因为它比 JWT 更贴合当前范围。

需要人工 Review 的主要是是否有未来部署 / 客户端约束要求 JWT；当前产品本身并没有这种驱动。

---

## 22.5 Deployment

产品没有定义部署平台、成本和 SLA，因此当前只能确认“单实例足够”，不能在本轮合理选择具体云厂商、VM、PaaS 或容器服务。

---
