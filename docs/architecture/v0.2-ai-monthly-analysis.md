## 1. Module Boundary

### A01 · 分析逻辑模块（Analysis Logical Module）

建立独立的分析逻辑模块。

当前仍然是一个 Spring Boot、一个 Maven 工程、一个进程、一个 MySQL，以及 Modular Monolith。逻辑上使用 package boundary。不拆微服务。本文不指定具体 Java 包名。

### A02 · 月度分析是第一个能力（Monthly Analysis as First Capability）

AI 月度分析是 Analysis Module 的第一个具体业务能力。

当前使用具体模型：`MonthlyAnalysisContext`、`MonthlyAnalysisSnapshot`、`GenerateMonthlyAnalysis`。

不提前泛化成通用分析框架（Generic Analysis Framework）。

### A03 · 面向业务的边界（Business-oriented Boundary）

顶层边界使用 `analysis`。不使用 `ai` 作为业务模块名称。AI / LLM 是实现技术。

### A04 · 单向依赖（One-way Dependency）

Analysis 依赖 Bookkeeping 的读取能力。Bookkeeping Core 不依赖 Analysis。禁止循环依赖（Circular Dependency）。

### A05 · 依赖公开读取边界（Depend on Public Read Boundary）

Analysis 不直接依赖 Core Repository、Persistence Entity、Internal Calculator、Database Table。

通过稳定的读取边界（Read Boundary）/ 端口（Port）获取账本事实（Bookkeeping Facts）。

### A06 · 分析模块拥有自己的 AI 数据（Own AI Data）

Analysis Module 自己拥有：

- 月度分析快照（Monthly Analysis Snapshot）
- 上下文指纹（Context Fingerprint）
- 分析配额 / 协调（Analysis Quota / Coordination）
- 来源元数据（Provenance Metadata）

Core 不管理这些数据。

### A07 · 提供方藏在分析边界之后（Provider Hidden Behind Analysis Boundary）

外部大语言模型提供方（External LLM Provider）位于 Analysis 技术边界之后。

### A08 · 不预先建立共享 AI 平台（No Premature Shared AI Platform）

MVP 不建立通用 AI 平台（Generic AI Platform）或共享 AI 框架（Shared AI Framework）。出现第二个真实 AI 能力之后，再从真实重复中抽象。

## 2. Application Boundary

### A09 · 读取与生成分成两个用例（Separate Read and Generate Use Cases）

区分查看月度分析（Get Monthly Analysis）与生成月度分析（Generate Monthly Analysis）。

打开页面不自动调用 LLM。

### A10 · 服务器重建当前上下文（Server Rebuilds Current Context）

每次生成，后端根据当前账本事实重新构建当前月度分析上下文（Current Monthly Analysis Context）。

前端提供的上下文（Context）或指纹（Fingerprint）只作为前置条件信息，不是权威事实。

### A11 · 应用层负责编排（Application Orchestrates）

应用层（Application Layer）负责编排（orchestration）。它不重新实现统计（Statistics）、交易汇总（Transaction aggregation）或分类计算（Category calculation）。

### A12 · 事实经过读取端口（Facts Through Read Port）

Analysis 通过稳定的读取端口（Read Port）获取账本事实。

### A13 · 分析模块构建上下文（Analysis Owns Context Construction）

Bookkeeping 提供事实。Analysis Module 构建月度分析上下文（Monthly Analysis Context）。

### A14 · 复用先于配额（Reuse Before Quota）

相同上下文可以直接复用已有 Snapshot。结果复用（Result Reuse）优先于产品配额（Product Quota）。

### A15 · 提供方藏在生成端口之后（Provider Hidden Behind Generator Port）

Application 调用业务化的生成器端口（Generator Port）。不直接依赖具体 Provider。

### A16 · 只有有效生成才创建快照（Only Valid Generation Creates Snapshot）

只有通过生成结果校验（Generated Output Validation）的结果才能创建 Snapshot。

### A17 · 失败不改变已有快照（Failure Does Not Mutate Existing Snapshot）

新的生成失败时，不删除、不修改、不覆盖已有 Snapshot。

### A18 · 用户可见的上下文新鲜度门禁（User-visible Context Freshness Gate）

生成前必须按 CR-001 验证：用户已查看的月度上下文，与服务器当前月度上下文是否一致。正式规则见 `docs/changes/v0.2-ai-monthly-analysis-cr-001-pre-analysis-freshness.md`。

不一致时返回 `REFRESH_REQUIRED`，并且不调用 LLM、不创建 Snapshot、不消耗产品配额。用户刷新数据后必须再次主动点击分析。

## 3. Provider Abstraction

### A19 · 业务专用生成器端口（Business-specific Generator Port）

Application 依赖月度分析生成器（Monthly Analysis Generator），而不是通用的 `AiClient`。

### A20 · 提供方适配器负责生成翻译（Provider Adapter Owns Generation Translation）

提供方适配器（Provider Adapter）负责：

月度分析上下文 → Prompt / Provider Request → Provider Response → 生成结果（Generated Result）。

具体 Prompt 与结构化输出（Structured Output）仍属于后续 AI-specific Design。

### A21 · 允许提供方专用的基础设施客户端（Provider-specific Infrastructure Client Allowed）

基础设施内部允许存在提供方专用客户端，包括 HTTP、认证（Authentication）、Provider DTO、Provider Error Mapping。该客户端不能暴露给 Application。

### A22 · 单一活动提供方与模型（Single Active Provider / Model）

MVP 每次部署只有一个活动提供方（Active Provider）和一个模型（Model），由配置确定。不允许用户动态选择模型。本文不选择具体厂商或商业模型。

### A23 · 不自动切换提供方（No Automatic Provider Fallback）

Provider 失败时，本次生成失败。MVP 不自动切换到第二个 Provider。

### A24 · 返回来源元数据（Provenance Returned）

成功的生成返回生成内容（Generated Content）、Provider、Model，以及保存 Snapshot 所需的来源元数据（Provenance Metadata）。

### A25 · 提供方错误不穿透（Provider Errors Do Not Leak）

Provider 的 HTTP、SDK 或异常不穿透生成器边界（Generator Boundary）。

## 4. Generation Flow / Concurrency

### A26 · 调用 LLM 前完成确定性预检查（Deterministic Pre-checks Before LLM）

调用外部 LLM 之前，完成本地可判断的条件：新鲜度确认（Freshness）、空月份（Empty Month）、结果复用（Result Reuse）、配额（Quota）、重复生成（Duplicate Generation）。

### A27 · 生成范围按上下文界定（Generation Scoped by Context）

生成范围（Generation Scope）是用户（User）+ 月份（Month）+ 上下文指纹（Context Fingerprint）。

### A28 · 同一范围只有一次飞行中的生成（Single-flight Generation）

同一生成范围同时最多一个外部 LLM 调用。

### A29 · 界面防护不是正确性（UI Prevention Is Not Correctness）

前端的 loading 或 disabled 可以防止重复点击。后端必须独立保证生成去重（Generation Deduplication）。

### A30 · 原子的生成认领（Atomic Generation Claim）

进行中检查与认领（Generation In Progress Check + Claim）必须具有原子语义（Atomic Semantics）。

### A31 · 校验先于快照（Validation Before Snapshot）

Provider Response 必须通过生成结果校验之后，才能创建 Snapshot。

### A32 · 快照与产品配额的一致性（Snapshot + Product Quota Consistency）

成功创建 Snapshot 与消耗产品配额，必须形成一个本地一致性结果。

### A33 · 不为并发去重引入重型分布式设施（No Heavy Distributed Concurrency Infrastructure）

MVP 不为并发去重引入 Redis Lock、消息队列（MQ）、分布式事务（Distributed Transaction）或独立 Worker 系统。使用 Spring Boot + MySQL 解决。

## 5. Persistence Boundary

### A34 · 快照与生成协调分开持久化（Separate Snapshot and Generation Coordination）

成功的 Snapshot 与生成协调（Generation Coordination）分开持久化。

### A35 · 快照只保存成功结果（Snapshot Contains Success Only）

快照存储（Snapshot Store）只保存成功并通过校验的不可变生成产物（Immutable Generated Artifact）。

不保存 `IN_PROGRESS`、`FAILED`、`TIMEOUT` 等状态。

### A36 · 生成协调是运行状态（Generation Coordination Is Operational State）

`IN_PROGRESS`、`FAILED`、重试（Retry）、租约（Lease）属于应用 / 运行持久化（Application / Operational Persistence）。它们不是 Snapshot 的领域状态。

### A37 · 持久化的生成认领（Durable Generation Claim）

单飞（Single-flight）不能只依赖 JVM 内存锁。使用 MySQL 持久化协调语义。

### A38 · 基于租约的恢复（Lease-based Recovery）

生成认领必须能在进程异常后恢复。通过生成租约（Generation Lease）或等价机制实现。具体时间值由后续 Design 决定。

### A39 · 数据库事务不跨越 LLM 调用（No Transaction Across LLM Call）

禁止数据库事务跨越外部 LLM 调用。执行形式是：短事务认领，提交，外部 LLM，短事务收尾（Finalization）。

### A40 · 原子的本地收尾（Atomic Local Finalization）

最终成功阶段在一个本地短事务中保持一致：创建 Snapshot、消耗已预留的产品配额、完成生成协调。

### A41 · 不承诺外部 LLM 恰好一次（No Exactly-once Promise for External LLM）

MVP 保证并发下的单飞。不承诺在进程崩溃、网络结果不明，或 Provider 在处理完成后超时的情况下，外部 Provider 恰好一次（Exactly-once）。

## 6. Result Reuse 与上下文指纹（Context Fingerprint）

### A42 · 快照复用是产品语义（Snapshot Reuse Is Product Semantics）

相同上下文复用已有 Snapshot。这不是普通缓存（Cache）。

### A43 · 不引入结果缓存基础设施（No Result Cache Infrastructure）

MVP 不引入 Redis、Caffeine 或基于 TTL 的 AI 结果缓存。Snapshot 持久化本身就是结果存储（Result Store）。

### A44 · 指纹只表示分析输入（Fingerprint Represents Analysis Input Only）

上下文指纹只表示月度分析上下文。它不包含 Provider、Model、生成时间（Generated Time）、Snapshot ID、HTTP Request ID 或数据库更新时间（DB Updated Time）。

### A45 · 先规范化上下文再计算指纹（Canonical Context Before Fingerprint）

顺序必须是：月度分析上下文 → 规范化上下文（Canonical Context）→ 指纹。规范化必须是确定的。具体规则由后续 Design 冻结。

### A46 · 指纹契约可以有版本（Fingerprint Contract Is Versionable）

规范化与指纹契约需要版本语义。具体算法由后续设计决定。

### A47 · 新鲜度与复用使用同一个上下文身份（Same Context Identity for Freshness and Reuse）

CR-001 的新鲜度确认与 Snapshot 结果复用，使用同一个分析上下文身份（Analysis Context Identity）。

### A48 · 调用 LLM 前预留配额（Quota Reservation Before LLM）

产品配额在成功时才最终消耗。进入 LLM 之前必须预留容量（Reserve Capacity），防止并发超额调用。

运行成本防护（Operational Cost Guard）仍以产品基线为准：它与产品配额是不同概念，本文不设计其实现。

### A49 · 生成许可（Generation Permit）

同一范围的单飞认领，加上配额预留，组成生成许可（Generation Permit）。获取必须具有原子语义。

### A50 · 配额归属使用许可日期（Quota Attribution Uses Permit Date）

每日额度归属按取得生成许可时的 `Asia/Shanghai` 自然日，不是 LLM 完成时间。

## 7. Failure / Timeout / Degradation

### A51 · 不自动重试 LLM（No Automatic LLM Retry）

MVP 的外部 LLM 调用失败后不自动重试。由用户以后主动重新生成。

### A52 · 关闭隐藏的提供方或 SDK 重试（Disable Hidden Provider / SDK Retry）

Provider SDK 或 HTTP Client 不允许在业务不可感知的情况下自动重复生成调用。

### A53 · 显式的生成超时（Explicit Generation Timeout）

外部 LLM 生成必须有超时（Timeout）或截止时间（Deadline）。具体数值在 Provider 选定后确定。

### A54 · 租约长于生成窗口（Lease Exceeds Generation Window）

生成租约必须大于最大生成执行窗口（Generation Execution Window）加安全余量（Safety Margin）。具体时间由后续设计决定。

### A55 · 已知失败立即释放许可（Known Failure Releases Permit Immediately）

已知失败立即释放生成许可和配额预留。进程崩溃通过租约到期（Lease Expiry）恢复。

### A56 · 无效输出是生成失败（Invalid Output Is Generation Failure）

HTTP 200 不等于成功的分析。生成结果校验失败时不创建 Snapshot。MVP 不进行第二次 LLM 修复调用（Repair Call）。

### A57 · 失败后已有快照保持不变（Existing Snapshot Survives Failure）

新的生成失败不改变已有 Snapshot。旧 Snapshot 与当前上下文不一致时，只体现为过期（STALE）这一派生状态（Derived State）。

### A58 · 界面生命周期不拥有生成生命周期（UI Lifecycle Does Not Own Generation Lifecycle）

页面退出不自动取消已经开始的后端生成。

### A59 · 内部分类与用户状态分开（Internal Failure Classification vs User State）

内部可以区分限流（Rate Limited）、超时（Timeout）、不可用（Unavailable）、无效输出（Invalid Output）、配置错误（Configuration Error）、持久化错误（Persistence Error）。

用户只暴露具有明确行动意义的稳定状态。本文不规定这组内部原因到用户状态的映射表。

### A60 · AI 失败不得拖垮记账核心（AI Failure Must Not Degrade Bookkeeping Core）

外部 AI 失败只能影响分析能力。不得影响登录（Login）、交易（Transaction）、余额（Balance）、流水（Ledger）、统计（Statistics）、分类（Category）等核心能力。

## 8. Synchronous Generation / Re-entry

### A61 · 同步生成执行（Synchronous Generation Execution）

MVP 使用同步生成执行。当前后端请求在取得生成许可后，直接完成外部 LLM 调用、校验和 Snapshot 收尾。

不引入后台 Worker、消息队列或作业系统（Job System）。

### A62 · 生成生命周期是持久的（Generation Lifecycle Is Durable）

执行路径是同步的。生成生命周期由持久化的生成协调状态（Generation Coordination State）管理。它不依赖 HTTP 连接或界面页面生命周期。

### A63 · 再次进入时恢复生成状态（Re-entry Restores Generation State）

用户退出后再进入时，查看月度分析必须能够恢复当前状态，例如：

- `CURRENT`
- `STALE`
- `GENERATION_IN_PROGRESS`
- `GENERATION_FAILED`
- `NO_ANALYSIS`
- `EMPTY_MONTH`

具体 API response shape 由后续设计决定。

### A64 · 进行中的生成阻止再次提交（Active Generation Prevents Resubmission）

存在同一生成范围的活动生成时，前端禁止再次提交。后端同时保证无法再次获取生成许可。

### A65 · 轻量轮询（Lightweight Polling）

MVP 对进行中页面允许轻量轮询，以发现成功或失败。不引入 WebSocket、SSE 或 Push。具体轮询间隔由后续 Frontend / API Design 决定。

### A66 · 失败是可再试的运行状态（Failure Is Retryable Operational State）

生成失败时不创建 Snapshot，也不产生成功的产品配额消耗。用户可以以后重新主动生成。

`FAILED` 属于生成协调 / 运行状态，不是 Snapshot 的领域状态。

## 9. Overall Generation Flow

成功路径：

```text
User requests Generation
↓
Backend rebuilds Current Monthly Analysis Context
↓
Freshness Check
    changed → REFRESH_REQUIRED
↓
Empty Month Check
    empty → NO_ANALYZABLE_ACTIVITY
↓
Canonical Context
↓
Context Fingerprint
↓
Existing Snapshot?
    yes → Result Reuse
↓
Acquire Generation Permit
    ├─ Active Same Scope
    │    → GENERATION_IN_PROGRESS
    └─ Daily Capacity Exhausted
         → QUOTA_EXCEEDED
↓
External LLM
↓
Generated Output Validation
↓
Local Finalization Transaction
    ├─ Create immutable Snapshot
    ├─ Consume reserved Product Quota
    └─ Complete Generation Coordination
↓
Return Snapshot
```

空月份的定义和用户语义以产品基线为准：收入交易笔数与支出交易笔数都为 0；不调用 External LLM，不创建 Snapshot，不消耗产品配额，不生成 AI 分析。提示所指是当前账本中未记录收入 / 支出。`NO_ANALYZABLE_ACTIVITY` 是这条已冻结产品行为在流程中的结果，不是新的产品规则。

失败路径：

```text
LLM / Validation / Finalization failure
↓
No new Snapshot
↓
Existing Snapshot untouched
↓
Release Permit if possible
or Lease Expiry recovery
↓
No successful Product Quota Consumption
```

## 10. State / Query Semantics

与 Domain Baseline 一致：

- Snapshot 是不可变的成功产物（Immutable successful artifact）。
- 最新（Latest）是查询语义（Query Semantic）。
- 当前 / 过期（Current / Stale）是派生状态（Derived State）。
- 生成协调（Generation Coordination）是运行状态（Operational State）。

`IN_PROGRESS` 与 `FAILED` 不写入 Snapshot 的领域状态。

## 11. Explicit Non-goals

本架构基线不引入：

- 微服务（Microservice）
- 独立 AI 服务（Separate AI Service）
- Python Service
- Redis
- MQ / Kafka
- 分布式锁（Distributed Lock）
- 分布式事务（Distributed Transaction）
- 向量数据库（Vector DB）
- RAG
- Agent
- WebSocket
- SSE
- 后台 Worker（Background Worker）
- 通用 AI 平台（Generic AI Platform）
- 提供方回退（Provider Fallback）
- 自动 LLM 重试（Automatic LLM Retry）

这些不是当前 MVP 的缺失项。

## 12. 后续 Design，不是未完成的架构

AI-specific Design 尚未开始，也未冻结。下列问题属于后续 Design。它们不表示 Architecture Baseline 未完成：

- 分析上下文契约（Analysis Context Contract）
- 规范化上下文（Canonical Context）的表示
- 指纹算法与版本格式（Fingerprint algorithm / version format）
- Prompt 契约（Prompt Contract）
- 结构化输出契约（Structured Output Contract）
- 生成结果校验的细节（Generated Output Validation details）
- 提供方选择（Provider selection）
- Provider 超时的具体数值
- 租约的具体数值（Lease exact values）
- Snapshot 表结构
- 生成协调的表或结构
- 每日配额的持久化表示
- API response shape
- 轮询间隔（Polling interval）
- 完整上下文快照（Complete Context Snapshot）是否持久化

产品基线另外写明：多条 Snapshot 对应同一上下文时选用哪一条，产品未指定。本基线不补这个选择。
