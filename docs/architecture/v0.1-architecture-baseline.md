# 记账软件 v0.1 · Architecture Baseline

> 文档状态：**Confirmed / Architecture Baseline**  
> 目标版本：v0.1  
> 上游基线：Product/UI Freeze、Architecture Context、Confirmed Domain Baseline、Reviewed Architecture Options  
> 用途：作为后续 Data Model、API Design、Implementation Plan 与 AI Coding 的正式架构输入。  
> 本文不包含数据库字段、ER 图、HTTP API、Java 包结构或代码。

---

## 1. System Context

```text
WeChat Mini Program / 微信小程序
            │
            │ authenticated application requests
            ▼
Independent Backend / 独立后端
Java + Spring Boot
Modular Monolith
            │
            │ MySQL local transactions
            ▼
MySQL
```

首个客户端为微信小程序。核心业务规则、认证、用户隔离、事务、一致性与持久化由可信后端执行。后端保持为单一部署单元，并为未来其他客户端保留可复用的业务边界。

---

## 2. Overall Architecture

采用 **Modular Monolith / 模块化单体**：

- 单一后端应用；
- 单一部署单元；
- 单关系数据库本地事务；
- 代码内部维持清晰业务模块边界；
- 模块化主要服务可维护性和 AI Coding Context 控制；
- 不引入复杂模块化框架；
- 不采用微服务。

Architecture Baseline 不在本阶段定义具体 Java Package。

---

## 3. Technology Baseline

- Backend Language：Java；
- Backend Framework：Spring Boot；
- Database：MySQL；
- Client：WeChat Mini Program；
- Persistence Style：Relational Persistence + MySQL Local Transaction；
- Authentication：Opaque Token + DB-backed Server Session；
- Development Mode：Local-first；
- Future Hosting：可部署至中国大陆云服务商，具体厂商/运行形态暂不冻结。

Java、Spring Boot、构建工具的精确版本进入工程初始化阶段确定。

---

## 4. Trust Boundary

可信边界位于后端：

- 客户端输入均视为不可信；
- 客户端不得通过提交 User ID 决定数据归属；
- 服务端通过 Session 建立 Trusted User Context；
- 核心业务规则和数据归属验证在服务端执行；
- 数据库提供事务、唯一性与持久化兜底。

微信小程序主要承担 UI、输入、展示和客户端交互状态。

---

## 5. Persistence Principles

1. 使用 MySQL 作为正式持久化数据库；
2. Transaction 与 BalanceAdjustment 分开持久化；
3. Category、Tag、Transaction-Tag Association、User、Account、Session 均以关系型持久化表达；
4. Ledger Entry 不作为核心持久化实体；
5. Balance 与 Statistics 保持派生语义，不作为 v0.1 的独立源事实；
6. 数据库设计不得反向改变 Confirmed Domain Baseline；
7. User Scope 需要进入数据归属与唯一性设计；
8. 具体表、字段、索引、约束进入 Data Model 阶段。

---

## 6. Transaction / Consistency Principles

核心写操作使用 MySQL 本地事务：

- CreateTransaction；
- EditTransaction；
- DeleteTransaction；
- CreateBalanceAdjustment；
- DeleteBalanceAdjustment。

Transaction 保存的一致性结果包括：

- Transaction 本身；
- Category Reference；
- 最终 Transaction-Tag Association Set。

CreateTag 是独立操作：Tag 创建成功后，后续 Transaction 取消或保存失败不回滚 Tag。

不使用分布式事务。

---

## 7. Balance Strategy

领域定义：

```text
Current Balance
= Opening Balance
+ Income Transaction Amount Sum
- Expense Transaction Amount Sum
+ Balance Adjustment Amount Sum
```

v0.1 技术策略：**Query-time Aggregation**。

不维护：

- persisted current_balance；
- Redis Balance；
- Balance Cache；
- 异步余额。

源业务事实始终是余额正确性的依据。

---

## 8. Statistics Strategy

Monthly Summary、Category Statistics、Tag Statistics 使用 **Query-time Aggregation**。

不建立：

- Summary Table；
- Redis Cache；
- MQ / Async Statistics；
- OLAP。

未来仅在真实性能证据出现后重新评估。

---

## 9. Idempotency

创建型保存操作使用组合保证：

1. Client 保存按钮禁用作为 UX 防护；
2. 每次保存意图生成 Operation ID / Idempotency Key；
3. 同一保存意图重试复用同一 Operation ID；
4. Server + MySQL Unique Constraint 形成最终幂等保证。

不引入 Redis Idempotency Platform。

具体字段及重复请求返回表达在 Data Model / API 阶段确定。

---

## 10. Concurrency

采用 **Account-level Database Pessimistic Lock Protocol**。

所有会改变同一 Account Balance 的操作都必须在事务内遵守统一账户锁协议：

- Create/Edit/Delete Transaction；
- Create/Delete BalanceAdjustment。

CreateBalanceAdjustment 顺序：

1. 获得 Account Lock；
2. 计算提交时 Current Balance；
3. 计算 `Adjustment Amount = Target Balance - Current Balance`；
4. 若差额非零，创建 BalanceAdjustment；
5. 提交事务。

不引入 Redis / Distributed Lock，不全局提升 Serializable 隔离级别。

---

## 11. Time / Ordering

四种语义必须分开：

### Business Record Time

用户选择的业务发生时间，用于 Calendar Month、Ledger 主排序和 Statistics 时间口径。

### First Saved Time

记录第一次成功保存进入系统的实际系统时点；普通编辑不得改变。

### First Save Order

用于同一 Business Record Time 秒内稳定排序，规则为：

```text
Business Record Time DESC
First Save Order DESC
```

采用 **Account-scoped monotonic database order**：

- Transaction 与 BalanceAdjustment 共享同一个账户范围保存顺序；
- 只在记录首次创建时分配；
- 编辑不改变；
- 分配发生在 MySQL 事务中；
- 创建操作已先获得 Account 行级锁，在同一个串行化边界内分配下一个顺序；
- 具体计数状态落在 Account 还是辅助表，由 Data Model 决定；
- 不要求全系统全局唯一；
- 不要求连续无 gap；
- 不用于用户展示。

### Updated Time

仅作为 Technical Metadata，可支持未来增量同步、BI/ETL、排障或技术审计；不参与 Balance、Calendar Month、Statistics 或 Ledger Sorting。

---

## 12. Authentication

采用 **Opaque Token + DB-backed Server Session**：

```text
Username + Password
        ↓
Authenticate
        ↓
High-entropy Opaque Token
        ↓
MySQL Server-side Session
        ↓
Trusted User Context
```

要求：

- Token 不承载需要客户端解析的业务身份；
- Session 可主动失效；
- Logout 使 Session 失效；
- 密码使用成熟自适应单向 Password Hash；
- 不使用 JWT / Refresh Token；
- 不使用 Redis Session；
- 具体算法和 Session Schema 下一阶段确定。

---

## 13. User Isolation

- 认证后由 Session 获取可信 User Context；
- Account、Transaction、BalanceAdjustment、Category、Tag 的 Command / Query 必须处于当前 User Scope；
- 不信任客户端提交的 User ID；
- 修改、删除、查询均验证资源 Owner；
- 数据库唯一性规则应纳入 User Scope；
- v0.1 不建设 RBAC、ACL 或 Family Permission System。

---

## 14. Backup / Restore

真实数据启用前必须具备：

- 可执行 MySQL Logical Backup；
- 备份副本与主数据库故障域分离；
- 明确恢复步骤或脚本；
- 至少一次完整 Restore Verification。

未来云数据库快照可以作为额外保障，但不替代可验证恢复路径。

备份频率、保留周期和具体存储位置在部署阶段决定。

---

## 15. Logging / Observability

v0.1 使用 **Minimal Operational Baseline**：

- 应用启动 / 停止日志；
- Error / Exception 日志；
- 保存失败诊断信息；
- 必要 Authentication Security Log；
- Request / Correlation ID；
- Health Check。

日志禁止记录 Password、完整 Opaque Token 及其他敏感认证信息。

暂不建设完整 Metrics Platform、Distributed Tracing、Elasticsearch Logging Stack 或 OpenTelemetry 全套体系。

---

## 16. Deployment Baseline

当前采用 **Local-first Development**：

```text
Developer Mac
+ Spring Boot
+ MySQL
```

用于 Coding、自动化测试、客户端/HTTP 联调和验收。

未来可部署到中国大陆云服务商，但当前不冻结：

- 云厂商；
- VM / Container / PaaS；
- Docker 是否作为最终包装方式。

Architecture Requirement：正式应用不得依赖开发机特有环境。Database Connection、Password / Secret、Environment、Logging、Runtime Configuration 应可外部化。

## 19. Revisit Triggers

以下情况出现时允许重新打开对应架构决定：

- 出现真实高并发、SLA、高可用或多实例需求；
- 单 Account 写竞争成为可测量瓶颈；
- Balance / Statistics 查询出现真实性能问题；
- 出现跨账户统一 Ledger 或更复杂账户体系；
- 引入家庭共享、复杂权限或多租户模型；
- 引入多个独立服务或独立团队；
- Session 数据库读取成为明确性能瓶颈；
- MySQL 无法低复杂度满足新的持久化/查询需求；
- 云平台约束使当前部署策略成本显著上升；
- Product CR 改变核心领域模型或一致性边界。

架构不因“未来可能”预先改变；只有新 Driver 出现时重新决策。
