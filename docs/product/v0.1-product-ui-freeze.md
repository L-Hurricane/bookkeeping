> 文档状态：已冻结（Product/UI Freeze）  
> 目标版本：v0.1  
> 阶段结论：产品与 UI 探索阶段结束，可进入技术设计阶段。

## 1. Freeze 状态

v0.1 已完成以下产品阶段工作：

- 正式产品需求确认；
- CR-001、CR-002 需求与交互变更确认；
- 核心交互流程更新并完成低保真可点击原型验证；
- UI 视觉方向确定；
- 高保真可点击原型 `v0.1-prototype-v2` 完成；
- 高保真原型已由用户实际完整操作验收；
- 表单滚动等原型实现 Bug 已修复并通过再次验收。

结论：**当前产品范围、业务规则、核心交互与 UI 基线已经足够作为后续技术设计输入，v0.1 正式进入技术设计阶段。**

Freeze 不表示未来永远不能修改，而表示从本节点开始，已冻结内容不能通过技术设计或实现阶段被隐式改写；业务变化需要显式进入变更流程。

## 3. v0.1 已冻结产品范围

### 3.1 In Scope

v0.1 包含：

1. 预先创建的用户名密码账号登录与退出；
2. 每个用户一个名为“微信”的资金账户；
3. 资金账户起始余额初始化；
4. 收入、支出交易的新增、查看、修改、删除；
5. 普通交易的选填交易名称；
6. 固定一级 / 二级收支分类；
7. 标签选择与随用随加；
8. 当前余额；
9. 余额调整记录的创建、查看、删除；
10. 按北京时间自然月查询流水；
11. 月度净收入、净支出、收支结余及交易笔数；
12. 分类统计及二级分类关联明细；
13. 标签统计及关联明细；
14. 首个客户端为微信小程序；
15. 数据持久保存、用户数据隔离、金额精确到分、备份恢复等已明确的数据与质量要求。

### 3.2 Out of Scope

v0.1 不包含：

- 公开注册、找回密码、第三方登录及账号绑定；
- 多资金账户创建；
- 账户间转账；
- 家庭共享、多人协作、角色权限；
- 分类新增、改名、删除、移动、合并；
- 标签改名、删除、合并及独立标签管理页面；
- 待确认交易状态及自动状态处理；
- 银行、微信等外部账单同步；
- 多币种与汇率换算；
- 股票、基金等投资资产管理和估值；
- 信用卡账期、还款日等专用模型；
- 预算、定期交易、复杂图表；
- 自定义时间范围及高级查询；
- 导入导出；
- OCR、语音、AI 记账；
- 已保存余额调整记录的修改；
- 历史时点余额对账 / 回溯矫正。

上述未来可能能力不应作为 v0.1 过度设计的理由提前实现。

## 4. 已冻结的重要业务规则

以下只保留会直接影响后续技术设计的重要规则，不替代完整 PRD 与 CR。

### 4.1 用户、账户与数据归属

- v0.1 使用预先创建的用户名密码账号；不提供公开注册和账号管理页面。
- 资金账户、交易、分类和标签均归属于用户。
- 用户只能查看和操作自己的数据；数据隔离不能仅依赖前端隐藏。
- v0.1 每个用户仅有一个名为“微信”的手工资金账户，不连接外部微信支付或账单。
- 币种固定为人民币。
- 起始余额默认 0，可为正数、0 或负数，最多两位小数；初始化后不提供直接修改入口。

### 4.2 余额

- 余额定义为：**起始余额 + 收入金额合计 − 支出金额合计 + 余额调整金额合计**。
- 所有金额保留自身正负号。
- 全部已保存记录立即影响当前余额，包括交易时间在未来的记录。
- 当前余额不随所选查询月份变化。

### 4.3 普通收入 / 支出交易

- 交易类型为收入或支出；新增时选择类型。
- 已保存交易的类型不可修改。
- 金额必填，可为正数或负数，不允许为 0，最多两位小数。
- 收入 / 支出类型与金额正负号语义相互独立，系统不得依据金额符号自动改变交易类型。
- 每笔交易必须关联资金账户和一个可记账分类。
- 分类必须与交易类型匹配。
- 标签选填，可多选；已选择标签必须与交易类型匹配。
- 交易名称选填、允许重名；名称为空时流水列表显示分类名称。
- 备注选填。
- 修改金额、分类、标签、时间、名称、备注时应更新原交易，不创建额外交易。
- 删除普通交易后，应撤销该交易对余额及统计的影响。

### 4.4 分类

- 分类区分收入 / 支出，最多两级。
- 无二级分类的一级分类可以直接记账。
- 有二级分类的一级分类只能作为分组，不能直接关联交易；交易关联其二级分类。
- 本期分类为固定数据，不提供分类管理功能。
- 收入预置分类包含“利息”，可直接记账。

### 4.5 标签

- 标签区分收入 / 支出，不支持层级。
- 同一用户下标签名称全局唯一，不因收入 / 支出类型分别允许重名。
- 新标签创建成功后即独立保存；即使随后取消当前交易，新标签仍保留。
- 未保存交易的标签关联不得产生已保存交易关联。
- 编辑交易时，标签关联变化仅随交易保存生效；放弃编辑保留原交易关联，但本次新创建的标签本身仍保留。

### 4.6 时间与排序

- 普通交易与余额调整均可选择记录时间，精确到秒。
- 默认当前时间。
- 记录时间不得早于资金账户创建时间。
- 允许选择过去、当前或未来时间。
- 记录时间决定记录所属自然月及流水主排序，不决定记录是否影响当前余额。
- 月份边界与时间展示使用北京时间。
- 流水主排序为交易 / 调整记录时间倒序。
- 同一秒内的记录按首次保存先后稳定排序，后保存者在前。
- 普通交易编辑不得改变“首次保存时间 / 首次保存顺序”这一同秒排序依据。

### 4.7 余额调整

- 用户输入目标余额；系统按提交时当前余额计算：**调整金额 = 目标余额 − 当前余额**。
- 目标余额可以为正数、0 或负数；调整金额必须非 0。
- 目标余额等于当前余额时不生成记录。
- 余额调整保存固定差额，不锁定账户余额。
- 余额调整记录影响当前余额，但不计入收入、支出、分类和标签统计。
- 余额调整没有分类和标签。
- 余额调整记录可选择历史或未来记录时间，但历史时间不意味着回溯计算历史余额。
- 已保存余额调整不可修改；需要变化时删除后重建。
- 删除余额调整后撤销其余额影响。
- 保存余额调整为一次直接提交操作，不增加额外二次确认步骤。

### 4.8 月度查询与统计

- 月度查询按北京时间自然月，允许历史月份和未来月份。
- 月度流水包含收入、支出和余额调整。
- 收支交易笔数不包含余额调整。
- 净收入为该月收入交易金额的带符号合计。
- 净支出为该月支出交易金额的带符号合计。
- 收支结余 = 净收入 − 净支出。
- 起始余额与余额调整不进入上述收支统计。
- 分类统计按收入 / 支出分别统计；一级分类汇总与二级明细不能重复相加。
- 一笔交易关联多个标签时，完整计入每个标签，不按标签数量平分。
- 不同标签统计可能覆盖同一笔交易，因此标签金额不得相加作为总收支。
- 整体收支总计必须按交易去重。
- 无标签交易仍进入月度总计，并提供“无标签”统计分组。

### 4.9 数据与质量

- 数据必须持久保存，退出、重启和重新登录后仍存在。
- 登录密码不得明文保存。
- 金额计算必须精确到分。
- 交易保存、修改、删除与余额、统计结果必须保持一致。
- 保存失败不得留下部分生效的数据。
- 一次保存操作不得因重复点击产生多笔记录。
- 删除前需要明确二次确认，并提示余额影响。
- 使用真实数据前必须具备可执行的备份与恢复办法。
- 最终交付应能在手机上实际使用。

## 5. 验收基线

### 5.1 七个主要验收场景

后续实现继续以以下产品交互场景作为核心验收输入：

1. 早餐支出；
2. 午餐外卖并新增标签；
3. 月底利息收入；
4. 余额调整；
5. 月度流水、分类统计和标签统计；
6. 保存前纠正分类；
7. 保存后纠正分类。

### 5.2 前五场景连续执行结果

已验收结果：

- 当前余额：**60.50 元**；
- 净收入：**0.50 元**；
- 净支出：**35.00 元**；
- 收支结余：**-34.50 元**；
- 收支交易：**3 笔**；
- 全部流水：**4 条**；
- 餐饮支出：**35.00 元**；
- 外卖标签支出：**30.00 元**；
- 余额调整：**-5.00 元**，进入流水但不计入收支统计。

### 5.3 补充关键验收

后续实现至少还需要保持以下结果：

- 目标余额可以调整到 0；
- 零差额不生成余额调整记录；
- 新标签创建后取消交易，标签仍然存在；
- 已保存交易编辑时类型不能切换；
- 同秒记录后保存者在前，编辑不改变首次保存排序依据；
- 负收入 / 负支出遵循既定余额与统计语义；
- 保存前纠正分类仅按最终分类保存一笔交易；
- 保存后纠正分类更新原交易，不改变整体金额、余额和无关标签统计。

这些场景应作为后续实现与自动化测试的重要验收依据。

## 6. Open UX Decision（不阻塞技术设计）

### 跨月份保存后的列表定位

尚未正式确认：

> 从某个月份的账户流水进入新增 / 编辑页面，如果保存后的交易属于其他月份，返回账户流水后是停留原月份，还是自动切换到交易所属月份？

当前高保真原型临时采用：

> 保留进入表单前所选月份；若记录属于其他月份，用 Toast 提示其归属月份，不自动跳转。

该行为只是当前原型方案，**不视为正式产品需求**。

本问题不改变交易时间、月份归属、余额计算、统计口径或核心数据模型，因此**不阻塞当前技术设计**。

## 7. Freeze 后的变更规则

### 7.1 产品业务变化：建立 CR

以下类型变化需要建立新的 Change Request，例如：

- 增加或删除业务功能；
- 改变余额计算规则；
- 改变收入 / 支出或余额调整语义；
- 改变交易编辑能力；
- 改变分类 / 标签规则；
- 改变统计口径；
- 新增业务状态；
- 改变 v0.1 In Scope / Out of Scope。

### 7.2 原型 / 实现 Bug：不建立 CR

如果系统未按已经确认的规则工作，属于 Bug，例如：

- 页面无法正常滚动；
- 已确认规则实现错误；
- 余额或统计数值计算错误；
- 排序不符合已确认规则；
- 表单保存与取消行为与已确认交互不一致。

修复 Bug 不改变产品基线。

### 7.3 可逆 UI 微调：原则上不建立业务 CR

例如：

- 颜色；
- 字号；
- 圆角；
- 间距；
- 卡片 / 列表视觉；
- Chip / Pill / Toast / 弹层的具体样式。

如果 UI 调整实际改变了业务语义、入口能力、状态或规则，则应升级为产品变更重新评审。
