## 1. 产品定位与用户流程

### 1.1 产品目标

交付一款可在微信小程序实际使用的个人消费记账软件，支持多资金账户收支记录、账户间转账、分类与标签管理、账本净值及收支分析，以及成本受控的月度/年度 AI 分析。以用户主动输入的记录为事实来源，不接入银行、微信支付等外部真实账户数据，不推断用户未记录的真实资产。

### 1.2 目标用户与边界

- 当前面向**单个自然人管理自己的账本**；可以记录其所理解的家庭资金，但不提供家庭多人协作或共享账本。
- **仅交付微信小程序客户端**；Web、iOS、Android、鸿蒙未来按需要扩展。
- 币种沿用人民币，金额精确到分；不实现多币种汇率转换。
- 记账语义以用户明确选择的金额、账户、分类、标签、业务时间为准，允许在合法业务边界内自主灵活使用。
- 统计与 AI 分析均只解释账本内数据；**“账本净值”不代表现实家庭完整净资产**。

### 1.3 三个产品领域

**录入端**（业务事实）→ **统计端**（确定性计算）→ **AI 分析端**（基于统计的解释与观察）。

三个领域是产品责任划分，不意味着必须拆成独立部署的技术服务。AI 不参与余额或收支结果的最终计算。

### 1.4 主要使用流程

首次进入 → 微信登录并确认必要协议 → 创建资金账户、设置起始金额 → 记录收入/支出或转账 → 查看账户流水与余额 → 必要时余额调整、管理分类/标签、归档账户 → 按时间与账户进行统计、逐层下钻 → 按月或年主动生成 AI 报告。

## 2. 功能范围与优先级

### 2.1 v1.0 必须形成的业务闭环（P0）

- 微信小程序用户登录、内部独立 User ID、数据隔离。
- 多资金账户（普通/信用）、创建、改名、余额展示、归档/恢复、永久删除及其影响确认。
- 收支交易创建、查看、编辑、更换资金账户、删除，保留既有交易功能。
- 账户间转账（转出与转入各自业务时间，完整修改与删除）。
- 收支分类和标签独立管理，最多三级，关联、改名、移动和删除。
- 起始金额、派生余额与独立余额调整。
- 账本净值趋势；收入/支出按分类与标签分布；时间/账户筛选、包含归档、逐级下钻及交易明细。
- 全账本自然月/自然年 AI 分析、每天最多3次外部调用、报告持久查看（当前约定纳入本版本）。

### 2.2 延后、不影响当前 v1.0 非公开验收

- **用户主动注销**：开发优先级最低；当前非公开自用/验证版可不完成。**正式面向公众运营前必须补齐**包括注销入口、身份核验、冷静期、可撤销流程、最终数据清理及符合届时规则的处理时限；不得把尚未实现误写成已支持。
- 手机号登录、微信与手机号绑定、两套已存在账号的合并：暂不实现；当前身份模型须预留，**最晚在上线手机号登录时完整支持账号合并及安全验证**。
- **信用账户额度上限提醒（P2）**：作为可选低优先级增强，工作量允许时实现；若影响核心业务交付可延后，不阻塞 v1.0 业务闭环。
- 完整操作审计、历史恢复、系统管理后台：进入技术/后续产品讨论，不因本稿承诺全部用户操作均可回放。

### 2.3 明确不纳入当前 v1.0

投资端记账、证券/基金估值、房产及完整家庭资产负债；多币种；银行/微信支付账单自动同步；信用卡账单周期/还款提醒/利息分期；账户共享协作；自动记账、周期交易、拆单记账、附件 OCR；AI 自由问答、自选账户 AI 报告、AI 投资建议；分类树历史版本查询及一键回滚。除发现业务无法闭环，不因竞品功能丰富而新增。

## 3. ID｜用户身份与数据边界

**ID-01 微信登录**：微信小程序是唯一正式客户端与登录入口。用户主动微信授权/确认必要协议后，经微信身份验证建立或进入其内部用户账号。手机号非注册必填项；昵称、头像非必要项。

**ID-02 内部用户身份**：内部 User ID 独立于小程序 OpenID；微信仅为登录身份之一。后续一个 User 可关联不同认证方式，而无需更换交易数据归属。

**ID-03 后续绑定与合并**：用户已通过微信注册，再经手机号核验绑定时仍是同一 User；若微信账号和手机号账号均已独立存在，必须识别冲突、验证双方身份、经用户确认后合并，不允许直接覆盖或静默合并。v1.0 只预留领域可扩展性，完整合并最晚在手机号登录上线时交付。

**ID-04 数据隔离**：用户只能访问、修改其拥有的资金账户、交易、分类、标签及报告；跨账户操作必须同属当前用户。

**ID-05 注销（延后）**：未来提供应用内明确入口；暂定**7个自然日冷静期**。冷静期内**主动完成登录即撤销**；仅打开小程序或后台刷新不应撤销。期满人工使用受控工具处理亦可，无须当前建设管理后台。正式注销后个人业务数据默认依法删除或不可逆匿名化；仅在有合法依据时限范围内保留必需数据，不以永久逻辑删除替代删除义务。上线前须复核适用法规和平台审核要求。此条仅定义后续必达规则，**不是当前 P0 交付项**。

**主要验收**：微信首次登录建立独立数据归属；再次登录可回到原账本；其他用户不能通过请求参数访问该账本；登录方式与资金账户不是同一概念。

## 4. AC｜多资金账户与生命周期

**AC-01 创建与名称**：用户可自由创建多个资金账户；每个账户有稳定 ID、名称、类型、起始金额，当前余额为计算结果。**同一用户有效及归档账户名称全局不重名**；其他用户可重名。名称可修改且不影响关联记录。

**AC-02 类型**：普通账户、信用账户。普通账户余额小于0给予提示但允许操作；信用账户小于0不警告，负数表示欠款。两者使用统一余额计算模型。

**AC-03 信用额度上限提醒（P2，可延后）**：信用账户允许用户填写可选“额度上限”；若新建或修改的资金变动使该账户账本欠款金额超过额度上限，给出提示，但**不强制禁止保存**。未填写额度时不提示。v1.0 不要求信用额度的实时可用额度展示、账期、还款提醒或其他信用卡专属功能。额度提醒为非核心增强，不阻塞基础信用账户记账。

**AC-04 起始金额**：创建时填写，默认0，可正可负；此后不直接修改。补录早于账户创建日期的历史交易**允许**，仅使派生余额变化，不回写起始金额；不增加起始金额生效日期。

**AC-05 账户归档**：归档仅改变账户使用状态和默认显示位置，所有交易、转账、余额调整及直接关联保持不变。归档账户可查历史、可恢复；不允许新增交易、转账、余额调整。修改涉及归档账户的历史交易或转账前，先恢复该账户。

**AC-06 归档余额**：归档不清零、不做补偿调整，也不改变其他账户余额；账户可带正余额、负余额或欠款归档，界面须让用户知悉。

**AC-07 永久删除**：从已归档账户进入删除。若账户有子业务记录，则提示关联普通交易/余额调整/转账数量及不可恢复后果；确认后删除账户与其关联源记录，不保留作为普通业务可访问的残余记录。无跨账户转账时不影响其他账户。

**AC-08 跨账户影响**：如果删除账户关联转账，则**整笔转账一并删除**；其他仍存在账户的转账记录消失、余额与历史流水/统计按剩余记录重算。系统必须在执行前显示受影响账户、转账条数、余额删除前后数值与变化，用户明确确认后才可执行。

**AC-09 安全执行**：删除影响预览与真正执行前必须核对数据未发生变化；不一致则重新计算、要求再次确认。所有关联删除要么全部成功，要么全部不发生。

**AC-10 恢复**：已归档账户可恢复使用；永久删除后的账户和交易不提供恢复功能。

**主要验收**：两账户可同存、同用户账户不能重名；归档不改变任一账面计算值；恢复后可继续录入；删除包含跨账户转账的账户时，影响预览准确、确认后另一侧派生余额按整笔转账删除重新计算。

## 5. TRF｜账户间转账

**TRF-01 业务定义**：转账（Transfer）是用户记录的**两个不同资金账户间等额资金转移**，一笔转账对应转出减少、转入增加；不代表实际银行到账确认，不属于普通收入或支出。

**TRF-02 创建**：指定当前用户的两个不同正常账户与正数转账金额；两侧金额相等、方向相反。创建后形成一笔稳定的转账业务身份。

**TRF-03 双时间**：独立保存转出业务时间与转入业务时间，默认均为当前时间并保持同步。用户可主动解除同步分别修改，可恢复同步；具体控件留待交互设计。用户可选择过去、现在或未来；**不强制转入时间晚于转出时间**。

**TRF-04 非在途模型**：允许在真实到账之前先录入完整转账，使用用户自行选择的转入时间。当前版本**不引入待到账/已到账状态、到账确认及自动入账流程**。

**TRF-05 账户流水**：转出一侧按转出业务时间排序与归属，转入一侧按转入业务时间排序与归属。同一转账可能跨月、跨年，历史时点统计按两侧各自指定业务时间计算。

**TRF-06 编辑与删除**：可修改金额、转出/转入账户、双侧时间，转账 ID 保持稳定；一笔转账整体删除，撤销两侧对应金额影响。无论修改、删除还是因账户永久删除而连带移除，均须保持两侧一致性。

**TRF-07 手续费**：转账不设置手续费字段；真实存在的转账手续费由用户自行记录为独立普通支出。

**主要验收**：A 向 B 转1000，A -1000、B +1000、收支合计不变；17日晚转出、18日入账，17日历史时点只出现转出影响；允许用户录入相反时间顺序；编辑金额与账户不生成第二笔转账；删除整笔后两侧资金影响均撤销。

## 6. TX｜收入、支出与账户流水

**TX-01 原有普通交易规则保留**：收入/支出类型、精确金额、交易名称、分类、标签、业务时间、备注、CRUD、名称搜索、月度流水与排序等已有能力延续。交易名称**选填，可重名**；空名称按现有类别回退逻辑显示（无分类时的回退文字在 UI 审阅中确认）。交易金额非0，允许带符号负数；收入 -100 仍是收入抵减，支出 -100 仍是支出抵减。

**TX-02 分类可选**：一笔收入或支出交易可以关联0或1个分类；选择时必须为交易类型匹配的**当前叶子分类**；无分类交易属于“未分类”统计组。这项**覆盖** v0.1“分类必填”规则。

**TX-03 标签可选且多选**：每笔交易可关联任意多个合法标签，父节点、子节点可同时显式关联；不会自动建立父子继承关联。新增标签即刻独立保存；用户取消当前交易或交易保存失败时，新标签仍存在，但不会产生不完整的交易-标签关联。

**TX-04 多账户选择**：新建普通交易必须选择一个当前用户的**正常状态账户**；只有一个可选账户可默认选中，多账户初始选择策略留给 UI。修改交易时允许改变资金账户；原交易 ID、首次保存时间、首次保存顺序不变，旧账户移除资金影响，新账户取得该资金影响。

**TX-05 不允许改交易类型**：已保存的收入不能编辑成支出或转账，反之亦然。类型改变应由用户删除/另建适当业务，不在编辑中直接切换。

**TX-06 交易时间与排序**：交易业务时间独立于首次保存时间、首次保存序、更新时间；流水按业务时间 DESC，再按首次保存序 DESC；同秒后首次保存的记录在前。日期时间精确到秒、人民币账本日期边界使用北京时间。允许补录账户创建前业务时间（覆盖 v0.1 限制），也允许未来时间。**所有已保存的未来时间普通交易立即影响当前账面余额**；业务时间仍决定流水的所属日期与指定历史时点的统计。

**TX-07 操作反馈**：保存失败不得部分生效；防止重复提交；用户取消未保存的新增/编辑时按原有交互确认是否放弃；删除普通交易前确认，删除后余额和统计按剩余事实重算。交易修改后的回跳页面、月份位置可沿用现有 UI，若受多账户切换影响由 UI 设计审核统一明确。

**主要验收**：交易从账户 A 改到 B，交易 ID/类型/首次保存序不变，A、B 的余额相应变化；一笔无分类无标签交易可以保存且进入总收支；负支出减少净支出、不被误识别为收入；相同业务时间的两笔交易排序稳定。

## 7. CT｜分类与标签的独立管理

### 7.1 核心差异

| 规则 | 分类 Category | 标签 Tag |
|---|---|---|
| 角色 | 单一收支归属维度 | 多维说明型维度 |
| 树结构 | 最多3级 | 最多3级 |
| 收入/支出 | **分类分收入、支出两种类型** | **标签不分收入、支出** |
| 一笔交易关联数 | 0或1 | 0到多个 |
| 可关联节点 | 仅当前叶子节点 | 任意级节点 |
| 关联父节点和子节点 | 不适用 | 可同时显式关联 |
| 创建子节点 | 父节点有直接交易关联则不可创建 | 不受直接交易关联限制 |
| 跨收支类型移动 | 禁止 | 不适用此限制 |

**CT-01 树形规则**：一个节点最多一个直接父节点，可为顶级节点；树深度不超过三级（收支类型仅为命名空间，不算一级分类节点）。禁止循环和将节点移到自己后代下；移动子树须检查所有后代深度。

**CT-02 叶子规则**：分类叶子节点是**当前没有子节点的分类**，可以处于第一级、第二级或第三级。只允许新交易选择叶子节点。分类若当前被交易直接关联，不允许其新增子节点，也不能通过节点移动使其成为非叶子节点。

**CT-03 名称唯一**：同一用户的**收入分类**跨层级全局名称唯一；**支出分类**跨层级全局名称唯一；收入与支出之间允许同名。**标签**在同一用户全部层级全局名称唯一，不区分收入支出；分类与标签也允许同名。创建与改名验证，忽略首尾无意义空白。

**CT-04 创建/改名/移动**：分类和标签均支持创建、改名、调整父节点。移动只改变节点的当前结构位置，节点 ID、交易直接关联保持不变。分类移动还必须保持其收入/支出类型，目标父节点不得有直接关联交易；标签没有此限制。

**CT-05 历史解释**：用户调整分类或标签的层级后，当前及历史交易均**按最新树组织和展示**；不保留按过去版本查询层级归属的功能，不因移动而修改原交易的直接分类/标签 ID。

**CT-06 删除约束**：任何有子节点的分类或标签均**不允许删除**。无子节点的节点允许删除，即使已有直接关联交易；删除前提示直接关联交易的数量、影响与后果，并由用户确认。

**CT-07 删除分类后果**：被删除分类的原关联交易变为**无分类（未分类）**；不删除交易、不更改金额、时间、账户、其他标签。

**CT-08 删除标签后果**：删除该标签与全部关联交易的显式关联，其他标签关联不变；不删除交易本身。

**CT-09 显式关联不继承**：选择父标签不自动选择其子标签，选择子标签也不自动写入父标签；移动标签后原交易所选标签集合完全不变。

**CT-10 一致性与留痕边界**：节点删除与关联清理必须完整成功或全部失败。用户提出系统行为应可追查，但**审计采集范围、脱敏、保存期限、日志方案和是否向用户提供操作历史**统一移交技术方案/后续产品讨论；不视为已批准完整事件溯源或数据恢复功能。

**主要验收**：被交易关联的分类 C 可以移入没有直接交易的 B1 且不超过三级，历史交易仍指向 C；不能把 B1（含子孙导致超深）移入三级 C；已有直接交易的分类不能因移动变父节点；标签 C 可移到已有直接标签关联的 B1，交易原本选中 B、C 仍是 B、C；删除叶子分类后原交易成为未分类；删除叶子标签仅移除该标签关联；跨收入/支出类型移动被拒绝。

## 8. BAL｜余额与余额调整

**BAL-01 派生值**：Balance 为派生计算结果，不是用户可直接修改的独立业务事实。基准公式：  
`账户余额 = 起始金额 + 带符号收入合计 − 带符号支出合计 + 转入合计 − 转出合计 + 余额调整固定差额合计`。

**当前账面余额**计入全部已保存的资金变动，包括业务时间为未来的普通交易、转账两侧资金变动及余额调整；不增设“待确认”状态或延迟生效功能。**指定历史时点余额/净值**则依据各笔记录的业务时间及转账两侧各自时间截止筛选。二者是不同查询口径：未来业务记录可能已经影响当前账面余额，但尚未纳入截至今天的历史时点净值。界面必须通过名称和统计时间范围避免混淆。

**BAL-02 余额调整**：每次调整由用户输入目标余额，保存**固定差额 = 目标余额 − 提交时当前余额**。差额允许正、负但不能为0；目标余额与当前余额可为0或负值。后续补录历史交易不重新修改已保存的调整差额。

**BAL-03 独立业务**：余额调整不是普通收入/支出，也不是转账，不关联收支分类或标签，不计入收入支出金额；可在账户流水查询。沿用原有“已保存调整不支持编辑，可经确认删除后重新创建”；提交无需增加额外二次确认，取消编辑按既有规则。

**BAL-04 账户状态**：余额调整归属于指定正常账户；已归档账户不可新建余额调整，恢复后可操作。永久删除账户时其余额调整一并清理。

**BAL-05 业务时间**：余额调整允许用户指定过去、当前或未来的业务时间，**包括早于资金账户创建时间的时间**；不再执行 v0.1 的“不得早于账户创建时间”校验。记录所选业务时间决定历史流水与时点统计归属，但调整差额仍始终按**实际提交时的当前账面余额**计算并固定保存；未来时间的已保存调整亦立即影响当前账面余额。具体使用方式由用户自行决定。

**主要验收**：起始金额1000，补录5元历史早餐，起始字段仍1000、余额995；当前余额100，调整到95，生成固定-5，即使之后补录历史交易也不改变-5；余额调整不出现在收支占比中。

## 9. ST｜统计端

### 9.1 统一范围与时间

**ST-01 统计结构**：三项核心能力：①账本净值变化，②支出分类/标签分布与明细，③收入分类/标签分布与明细。不为 v1.0 扩大其他复杂报表。

**ST-02 时间范围**：优先提供**本月、本季度、本年、自定义时间区间**；以北京时间自然月、自然季度、自然年为准。用户习惯以月、季、年查看。可在后续 UI 设计考虑“近一个月/近一个季度/近一年”等次级入口，但不是本轮必备新增需求。

**ST-03 账户筛选**：**所有统计**支持选择资金账户，包括已归档账户。支持全部正常账户、全部账户、自定义多选；**默认选中全部正常账户**（可在 UI Review 核对）。归档只是当前可见/可选状态，不抹除历史事实；已永久删除的账户不可再选。明细继承时间、账户、收入/支出类型等条件。

### 9.2 净值

**ST-04 账本净值**：净值仅限账本中已保存的资金账户，允许含普通账户和信用账户（负值抵减）。不计算未录入软件的证券、房产、房贷、投资资产。所选账户净值为所选账户在该时点余额之和；选择全部账户可查看整个账本范围。对外不宣称“完整家庭净资产”。

**ST-05 净值趋势**：按选定时间段展示期初、期末或时间点净值及变化；**转账两侧分别按用户填写的转出/转入业务时间影响对应历史时点余额**，允许跨日期区间暂时出现两侧未抵消；普通交易与余额调整也按其业务时间参与历史时点计算。须与 BAL-01 所述“当前账面余额立即包含未来已保存记录”区分，避免把历史时点净值和不受业务时间限制的当前账面余额误认为同一指标。具体折线或颗粒度在 UI 阶段确认。

### 9.3 收入、支出与层级统计

**ST-06 独立收支统计**：收入、支出分别展示。采用带符号金额口径，与普通交易原有正负金额规则一致；起始金额、转账与余额调整**均不计入收入支出**。

**ST-07 分类分布**：所选收支类型、时间、账户范围内，每笔交易归属于唯一叶子分类或“未分类”。分类汇总互斥、完备，**必须包含未分类**；各分类带符号金额合计恒等于对应总收入/总支出金额。**占比采用带符号金额 ÷ 对应净总额的绝对值 × 100%**，从而正数金额显示正占比、负数金额显示负占比，不过滤负数记录。净总额为正时占比代数和为100%；净总额为负时为-100%；净总额为0时只展示金额、不计算百分比。正常使用场景下“分类占比合计100%”仍成立，负净额是数学例外，不能在保持负项负百分比的同时强制显示合计+100%。

**ST-08 标签覆盖率**：一笔交易可同时关联多个标签，各标签金额完整计入；每个标签占比以**当前收支类型、时间及账户范围内的全部收入/支出净总额的绝对值**为固定分母，分子是该标签子树内去重后的带符号金额。只选某些标签不缩小占比分母；正金额为正占比、负金额为负占比。不同标签占比**允许合计超过100%或低于0%**，不分摊交易金额。净总额为0时不计算百分比，仅展示金额。

**ST-09 标签树去重**：查询任一标签时，将该标签及其全部后代标签**显式关联的交易取并集**，按交易 ID 去重后计算；选择多个标签时合并各自子树后再按交易去重。父标签下钻同时显示子标签入口及“**直接关联本标签**”明细入口；后者仅看显式关联该标签的交易。同一交易可出现在不同明细入口，但父标签总额不能重复计入。

**ST-10 统一下钻**：收入、支出的分类与标签尽量保持统一操作：总体 → 子级分布 → 交易明细；明细持续继承当前筛选条件。分类子级互斥，标签子级可能交叠，必须避免误导性简单累加。历史交易统一按最新分类/标签层级解释。

**负数统计口径（RV-02 已确认）**：负收入、负支出仍按原交易类型统计，并可产生负百分比；当净总额为负时，分类百分比代数和为-100%，不是强制+100%；净总额为0时占比不可计算，应显示金额与明确的无占比状态。不调整交易事实，也不改变用户自行解释其记账方式的权利。

**主要验收**：同月餐饮400、交通300、未分类300，总支出1000，对应40%/30%/30%；正常收入/支出净额为80，其中正向100与负向-20分别显示125%和-25%；净总额为负时负项仍为负百分比且合计-100%；净额为0时仅展示金额、不展示虚假占比。同一100元交易同时关联父标签旅行和子标签北京，旅行树汇总只记100元；多个标签各自统计允许总体大于100%；选旅行标签后旅行占全部支出比重不变；归档账户可主动勾选参与所有统计；明细继承此前选择的账户、时间及收支类型。

## 10. AI｜轻量 AI 财务分析

**AI-01 范围**：针对用户**全部未永久删除账户**的**整个账本**，**必须包含已归档账户**。不允许自选某几个账户形成定制 AI 分析，不提供自由问答。

**AI-02 时间**：仅允许用户选择一个**自然月**或一个**自然年**（如2026年10月、2025年全年）；不支持自定义跨月范围、自然季度 AI 报告或随意指定天数。

**AI-03 发起**：由用户主动触发生成，不要求自动周期报告或后台定时推送。

**AI-04 成本限制**：沿用**单用户每日最多3次外部 AI 模型调用**的上限。报告重复查看不应触发新调用；超出上限应明确告知。

**AI-05 分工**：余额、收入、支出、分类、标签汇总等由系统按确定性业务规则计算，AI 只进行解释与观察，不作为账务事实源，不擅自把重叠标签汇总相加。

**AI-06 报告内容**：可包括期间账本净值变化、收入/支出结构、主要分类和标签、与适当历史期间对比的变化观察。不得从账本范围推断真实家庭总资产，避免无依据的消费道德评价或投资结论。

**AI-07 报告保存**：生成后可以保存并反复查看，避免重复付费调用；报告反映生成时输入的数据状态，历史交易后续变更不应静默篡改已生成报告。如支持重新生成，仍受调用次数限制。传输给模型的数据遵循最小必要范围，避免默认上传原始敏感备注、账号身份等。

**主要验收**：AI 分析无账户选择入口但纳入已归档账户；同一报告二次查看不调用模型；第4次外部调用被拦截；月份/年度之外时间组合不可选；AI 展示的财务数字可追溯到统计端计算结果。

## 11. 非功能验收与发布边界

**NF-01 精确性**：金额精确到分，禁止因浮点误差造成余额差异；跨账户转账/修改/删除、分类标签删除与关联变更具备一致性。

**NF-02 幂等与失败**：重复提交不能重复生成源业务记录；网络异常、重试或保存失败不产生部分资金变动。

**NF-03 安全隔离**：用户归属和权限由服务端校验；小程序端不应凭展示隐藏实现安全隔离；微信身份凭证与服务端会话遵循必要安全要求。

**NF-04 时间语义**：业务时间、首次保存时间、首次保存序与更新时间分离，不能以更新时间影响业务排序；所有自然周期按北京时间。

**NF-05 可使用与可验证**：微信小程序端能完成实际手工记账闭环；可执行的初始化、运行、验证及数据备份/恢复办法应在技术/发布方案中交付。

**NF-06 发布条件**：可验收、可部署不等于已经正式公众运营。真实运营前必须完成注销能力、必要的隐私协议及合规/平台要求核对；运营后台不是 v1.0 业务范围必需项。

**NF-07 技术审计另议**：运行日志、用户操作审计、脱敏、留存期限及恢复可能性在技术方案阶段讨论，不因本稿引入事件溯源系统、版本树恢复产品或重型管理平台。

## 13. 首轮 Review 结论与旧版差异说明

2026-10-18 用户已逐项反馈 RV-01～RV-04，其他章节表示无异议；2026-10-21 项目负责人已最终批准本 v0.2 修订内容并升格为 v1.0 Product Baseline。以下为落实结果。

| Review 项 | 用户结论 | v0.2 已落实到 |
|---|---|---|
| RV-01 未来时间与余额 | 未来时间的**已保存记录立即影响当前账面余额**；不增加待确认状态 | TX-06、BAL-01、BAL-05、ST-05 |
| RV-02 负数百分比 | 按带符号金额计算、负数为负百分比；用户自行解释使用场景 | ST-07、ST-08、验收场景 |
| RV-03 信用额度 | 信用账户可有额度上限，**仅超限提示**；低优先级，可延后 | AC-03、2.2 |
| RV-04 余额调整时间 | 允许用户指定早于账户创建的历史业务时间 | BAL-05、验收场景 |

### 13.1 RV-01 的特殊解释

旧版 MoneyWiz 式“未来记录待确认”不作为本版本强制流程。用户多年使用中习惯将记录直接视作确认；系统允许为未来日期保存记录，并立即调整当前账面余额。其**业务时间**仍控制列表月份和历史时点净值，两种口径应明确命名，不能误写成“未来记录等到日期到达才扣减当前余额”。

### 13.2 RV-02 的数学例外说明

负数占比和分类总占比100%并非对任意净额都能同时成立。当净额为正时，采用分母为净总额的绝对值，带符号占比代数和为100%；当净额为负时，带符号占比代数和为-100%；净额为零时没有合法百分比分母。**这只是同一通用公式的数学结果，不新增交易限制或人为调账功能。**

### 13.3 RV-05 既有代码差异（技术审核阶段）

需重点核对旧版单微信资金账户、用户名密码登录、分类必选、标签区分收支类型、两级分类、重复“其他”子分类名称、账户创建前业务时间限制、同账户首次保存序、统计口径、跨账户转账与账户删除联动等。旧版既定的**未来记录立即影响当前余额**、**余额调整保存固定差额**继续有效；有冲突的规则以正式批准的 v1.0 PRD 为准。代码更改须先经技术方案及 Stage/Task 审批。
