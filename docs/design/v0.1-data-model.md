# 1. Design Principles / 设计原则

本数据模型遵循以下已冻结原则：

1. `Transaction` 与 `BalanceAdjustment` 分开持久化；
2. `Balance` 是 Derived Value，不建立余额源事实表，也不保存 `current_balance`；
3. Monthly / Category / Tag Statistics 均 Query-time Aggregation，不建立 Summary Table；
4. `Ledger Entry` 只是 Read Model，不建立 Ledger 表；
5. 所有业务数据按可信 `User Scope` 隔离；
6. 所有影响账户余额的写操作遵守 Account-level pessimistic lock；
7. `Transaction` 与 `BalanceAdjustment` 共用 Account-scoped `First Save Order`；
8. Money 使用精确十进制，不使用 FLOAT / DOUBLE；
9. Business Record Time、First Saved Time、First Save Order、Updated Time 语义严格分离；
10. Operation ID / Idempotency Key 通过 MySQL 唯一约束形成最终防重复保证；
11. 不为了未来版本提前加入多账户转账、预算、AI、家庭共享、RBAC、汇总表等结构。

# 2. Table Inventory / 表清单

v0.1 共 **9 张持久化表**，其中 8 张业务/会话表 + 1 张轻量幂等技术表：

- `ledger_entries`
- `monthly_summaries`

# 3. Common Type Conventions / 通用类型约定

## 3.1 Identifier

业务实体主键统一建议：

```text
BIGINT AUTO_INCREMENT
```

原因：

- MySQL 原生支持；
- Java `long / Long` 映射自然；
- 当前不存在分布式 ID Driver；
- ID 仅用于内部身份，不承担 First Save Order。

---

## 3.2 Money

Money 使用：

```text
DECIMAL(19,2)
```

适用于：

- Opening Balance；
- Transaction Amount；
- Adjustment Amount。

要求：

- 不使用 FLOAT / DOUBLE；
- 普通 Transaction Amount 必须非 0；
- Opening Balance 可正、零、负；
- Adjustment Amount 必须非 0；
- `DECIMAL(19,2)` 的容量属于技术容量，不是产品对用户金额上限的新需求。

Java 层应使用精确十进制类型，不转换为二进制浮点数参与业务计算。

---

## 3.3 Business Record Time

普通交易与余额调整使用：

```text
DATETIME(0)
```

语义：

> Asia/Shanghai / 北京时间下的业务记录时间，精确到秒。

该字段是业务时间，不依赖：

- MySQL Server Time Zone；
- JVM 默认 Time Zone；
- 开发机默认 Time Zone。

应用负责将 API 输入解析为北京时间语义后持久化。

---

## 3.4 Technical Time

技术系统时间统一以 UTC 语义保存，建议：

```text
DATETIME(6)
```

典型字段：

- `created_at_utc`
- `first_saved_at_utc`
- `updated_at_utc`
- `expires_at_utc`

这些字段不承担 Calendar Month 或 Ledger 主排序语义。

---

## 3.5 Transaction Type

逻辑值：

```text
INCOME
EXPENSE
```

物理建议：

```text
VARCHAR(16)
```

数据库可以使用 `CHECK` 作为辅助保护，但正式业务校验仍由后端完成，不把正确性依赖于未确认版本的 MySQL CHECK 行为。

# 6. `idempotency_records`

## 6.1 Responsibility

轻量技术表，用于满足创建型操作的服务端幂等。

它不是业务领域实体，也不是通用“幂等平台”。

必须支持：

- CreateTransaction 重试；
- CreateBalanceAdjustment 重试；
- BalanceAdjustment 的 `NO_CHANGE` 结果，即使没有业务记录也要可重放；
- 业务记录后续被显式删除后，旧 Create Request 不会因为 Key 消失而重新创建。

## 6.2 Columns

| Column | Type | Null | Description |
|---|---|---:|---|
| `id` | BIGINT AUTO_INCREMENT | No | PK |
| `user_id` | BIGINT | No | 请求所属 User |
| `scope` | VARCHAR(64) | No | 如 `CREATE_TRANSACTION` / `CREATE_BALANCE_ADJUSTMENT` |
| `operation_id` | VARCHAR(64) | No | Client Idempotency Key |
| `request_hash` | BINARY(32) | No | 规范化请求内容 Hash |
| `result_code` | VARCHAR(32) | No | `CREATED` / `NO_CHANGE` 等 |
| `resource_id` | BIGINT | Yes | 创建成功时的业务资源 ID；无业务记录时 NULL |
| `created_at_utc` | DATETIME(6) | No | 幂等结果首次确定时间 |

## 6.3 Constraints

- PK: `id`
- FK: `user_id -> users.id`
- UNIQUE: `(user_id, scope, operation_id)`

语义：

- 同 Key + 同 Scope + 同 User + 同 Request Hash：重放已有结果；
- 同 Key + 同 Scope + 同 User + 不同 Request Hash：`IDEMPOTENCY_CONFLICT`；
- 不同 Scope 可以使用相同 Operation ID，但客户端仍应生成高随机唯一 Key。

## 6.4 Transaction Semantics

`idempotency_records` 必须与对应创建操作处于同一个 MySQL Local Transaction 中。

CreateTransaction：

1. 检查 / 建立 Idempotency Record；
2. 创建 Transaction + Associations；
3. 将 `resource_id` 和 `result_code=CREATED` 固化；
4. Commit。

CreateBalanceAdjustment：

1. 检查 / 建立 Idempotency Record；
2. Account Lock；
3. 重新计算 Current Balance；
4. 若差额为 0，记录 `result_code=NO_CHANGE`、`resource_id=NULL`；
5. 若非 0，创建 BalanceAdjustment 并记录 Resource ID；
6. Commit。

这样即使 NO_CHANGE 不生成业务记录，重复请求也保持同一结果。

## 6.5 Indexes

- `uk_idempotency_user_scope_operation(user_id, scope, operation_id)`
- `idx_idempotency_created(created_at_utc)`

v0.1 数据量很小，暂不设计清理策略；未来若需要 TTL/归档，再由真实数据规模驱动。

# 7. `accounts`

## 7.1 Responsibility

表示资金账户。

v0.1 每个用户只有一个：

```text
name = 微信
currency = CNY
```

同时承担 Account-scoped `First Save Order` 的数据库计数状态。

## 7.2 Columns

| Column | Type | Null | Description |
|---|---|---:|---|
| `id` | BIGINT AUTO_INCREMENT | No | PK |
| `user_id` | BIGINT | No | Owner |
| `name` | VARCHAR(64) | No | v0.1 固定“微信” |
| `currency` | CHAR(3) | No | v0.1 固定 `CNY` |
| `opening_balance` | DECIMAL(19,2) | No | 起始余额 |
| `created_time` | DATETIME(0) | No | 账户创建业务时点，北京时间；也是业务记录时间下界 |
| `last_first_save_order` | BIGINT | No | 已分配的最大 Account-scoped First Save Order，初始 0 |
| `updated_at_utc` | DATETIME(6) | No | 技术更新时间 |

## 7.3 Account Initialization

推荐：

> Account Row 在用户第一次完成账户初始化时创建，而不是在用户账号预创建时提前创建。

理由：

- `Account Creation Time` 与真实账户初始化时点一致；
- 不会因为部署时提前建账户而人为放宽“业务时间不得早于账户创建时间”的边界；
- 初始化前不允许创建 Transaction / BalanceAdjustment。

初始化后：

- `opening_balance` 不提供直接修改能力；
- 后续差异只能通过 BalanceAdjustment 修正。

## 7.4 Constraints

- PK: `id`
- FK: `user_id -> users.id`
- UNIQUE: `user_id`  
  v0.1 从数据库层保证每用户最多一个 Account。
- `currency = CNY`：Application Constraint，可辅以 CHECK。
- `last_first_save_order >= 0`

为后续复合 Ownership FK，可增加：

- UNIQUE: `(id, user_id)`

## 7.5 First Save Order Allocation

正式落地选择：

> **把 Account-scoped monotonic counter 存在 `accounts.last_first_save_order`。**

创建 Transaction / BalanceAdjustment：

1. `SELECT account ... FOR UPDATE`
2. 验证 Account 属于当前 User；
3. `last_first_save_order = last_first_save_order + 1`
4. 新值赋给新记录的 `first_save_order`
5. 在同一 MySQL Transaction 中创建业务记录
6. Commit

规则：

- Transaction / BalanceAdjustment 共用一个 Counter；
- Account Scope 即可，不要求跨用户全局顺序；
- 允许 Gap；
- 删除记录不回收 Order；
- Edit 不重新分配；
- Counter 不向用户展示。

## 7.6 Indexes

- `uk_accounts_user(user_id)`
- `uk_accounts_id_user(id, user_id)`

## 7.7 Evolution Note / v1.0 多账户演进说明

`UNIQUE(accounts.user_id)` 是 **v0.1-specific database constraint**。

v0.1 正式语义：
- 每个 User 最多一个默认 Account「微信」；
- User 不能自行新增、删除 Account；
- Account Row 在首次完成 Opening Balance 初始化时创建。

已知 v1.0 方向：
> User 默认可以没有 Account，并支持自行创建多个 Account。

该方向不属于 v0.1 Scope。v0.1 不提前移除唯一约束，也不提前实现 Account Management、Transfer 或 Multi-account Ledger。

进入 v1.0 时，通过 Product CR、Domain Impact Analysis、Architecture/Data Model Review 和 Database Migration 显式调整 `UNIQUE(accounts.user_id)` 及相关能力。

原则：已知未来会变化，不等于现在放弃对当前版本不变量的数据库保护。

# 8. `categories`

## 8.1 Responsibility

保存每个 User 的固定收入/支出分类。

v0.1：

- 无分类新增 API；
- 无修改、删除、移动、合并；
- 在用户准备/初始化阶段预置。

## 8.2 Columns

| Column | Type | Null | Description |
|---|---|---:|---|
| `id` | BIGINT AUTO_INCREMENT | No | PK |
| `user_id` | BIGINT | No | Owner |
| `type` | VARCHAR(16) | No | `INCOME` / `EXPENSE` |
| `name` | VARCHAR(100) | No | 分类名称 |
| `parent_id` | BIGINT | Yes | 一级分类为 NULL，二级分类指向父分类 |
| `parent_scope_id` | BIGINT generated | No | `COALESCE(parent_id, 0)`，只用于唯一性 |
| `created_at_utc` | DATETIME(6) | No | 技术创建时间 |

`parent_scope_id` 是物理约束辅助列，不属于领域字段，也不暴露 API。

## 8.3 Constraints

- PK: `id`
- FK: `user_id -> users.id`
- FK: `parent_id -> categories.id`
- UNIQUE: `(user_id, parent_scope_id, name)`

该唯一约束同时满足：

- 同一 User 一级分类名称唯一；
- Income / Expense 一级分类也不能重名；
- 同一父分类下二级名称唯一；
- 不同父分类下二级名称可以相同。

建议增加：

- UNIQUE: `(id, user_id, type)`

供 Transaction Composite FK 使用。

## 8.4 Application Constraints

数据库结构无法简洁表达的业务规则由 Application 强制：

- 最多两级；
- Parent 和 Child 必须属于同一 User；
- Parent 和 Child 类型一致；
- 有 Child 的一级分类不可直接记账；
- 无 Child 的一级分类可直接记账；
- 二级分类可直接记账；
- 名称保存前 Trim，Trim 后不得为空。

由于 v0.1 分类是固定 Seed Data，上述规则同时在 Seed Verification 中验证。

## 8.5 Indexes

- `idx_categories_user_type(user_id, type)`
- `idx_categories_parent(parent_id)`
- `uk_categories_scope_name(user_id, parent_scope_id, name)`
- `uk_categories_id_user_type(id, user_id, type)`

# 10. `transactions`

## 10.1 Responsibility

普通收入/支出源业务事实。

## 10.2 Columns

| Column | Type | Null | Description |
|---|---|---:|---|
| `id` | BIGINT AUTO_INCREMENT | No | PK |
| `user_id` | BIGINT | No | Owner |
| `account_id` | BIGINT | No | 所属 Account |
| `type` | VARCHAR(16) | No | `INCOME` / `EXPENSE`，首次保存后不可修改 |
| `amount` | DECIMAL(19,2) | No | 有符号金额，必须非 0 |
| `name` | VARCHAR(255) | Yes | 选填交易名称 |
| `category_id` | BIGINT | No | 可记账分类 |
| `business_time` | DATETIME(0) | No | 北京时间业务发生时间 |
| `first_saved_at_utc` | DATETIME(6) | No | 首次成功保存系统时间，编辑不变 |
| `first_save_order` | BIGINT | No | Account-scoped immutable order |
| `updated_at_utc` | DATETIME(6) | No | 技术更新时间 |
| `remark` | TEXT | Yes | 备注 |

## 10.3 Constraints

- PK: `id`
- FK: `(account_id, user_id) -> accounts(id, user_id)`
- Composite FK: `(category_id, user_id, type) -> categories(id, user_id, type)`
- UNIQUE: `(account_id, first_save_order)`

辅助 CHECK / Application：

- `amount <> 0`
- `type IN ('INCOME','EXPENSE')`
- `first_save_order > 0`

## 10.4 Application Constraints

必须由业务层验证：

- Account 属于当前 Trusted User；
- `business_time >= account.created_time`；
- Category 是可记账分类；
- Transaction Type 不可在 Edit 时改变；
- Tag Association 全部同 User、同 Transaction Type；
- Amount 最多两位小数；
- Name 可 NULL / 空白归一化策略；
- Remark 可选。

## 10.5 Idempotency

CreateTransaction 的 Operation ID 不存入 `transactions`，而由 `idempotency_records` 持久化。

这样：

- 重试与业务记录生命周期解耦；
- Transaction 后续被显式删除后，旧 Create Request 仍不会重新创建；
- 同一机制可处理 BalanceAdjustment 的 NO_CHANGE。

## 10.6 Indexes


核心：

- `uk_transactions_account_order(account_id, first_save_order)`
- `idx_transactions_ledger(account_id, business_time, first_save_order)`
- `idx_transactions_month_type(account_id, type, business_time)`
- `idx_transactions_category_month(account_id, category_id, business_time)`

说明：

MySQL B-Tree 可反向扫描，因此不依赖特定 Descending Index 才能执行 Ledger DESC 排序。

# 11. `transaction_tags`

## 11.1 Responsibility

表示已保存 Transaction 与 Tag 的关联事实。

## 11.2 Columns

| Column | Type | Null | Description |
|---|---|---:|---|
| `transaction_id` | BIGINT | No | Transaction |
| `tag_id` | BIGINT | No | Tag |

## 11.3 Constraints

- PK: `(transaction_id, tag_id)`
- FK: `transaction_id -> transactions.id ON DELETE CASCADE`
- FK: `tag_id -> tags.id ON DELETE RESTRICT`

PK 天然保证：

> 同一 Transaction 不会重复关联同一个 Tag。

- PK `(transaction_id, tag_id)`
- `idx_transaction_tags_tag(tag_id, transaction_id)`  
  支持 Tag Statistics 与 Tag Drill-down。

# 12. `balance_adjustments`

## 12.1 Responsibility

保存固定 Adjustment Amount。

不保存：

- Category；
- Tag；
- Income / Expense Type；
- Source-of-truth Target Balance。

Target Balance 是创建命令输入，最终源业务事实是 Adjustment Amount。

## 12.2 Columns

| Column | Type | Null | Description |
|---|---|---:|---|
| `id` | BIGINT AUTO_INCREMENT | No | PK |
| `user_id` | BIGINT | No | Owner |
| `account_id` | BIGINT | No | 所属 Account |
| `adjustment_amount` | DECIMAL(19,2) | No | 固定调整差额，非 0 |
| `business_time` | DATETIME(0) | No | 北京时间业务记录时间 |
| `first_saved_at_utc` | DATETIME(6) | No | 首次保存系统时间 |
| `first_save_order` | BIGINT | No | 与 Transaction 共用 Account Scope 顺序 |
| `remark` | TEXT | Yes | 可选备注 |

BalanceAdjustment 不可编辑，因此不额外保存业务无意义的 `updated_at_utc`。

## 12.3 Constraints

- PK: `id`
- FK: `(account_id, user_id) -> accounts(id, user_id)`
- UNIQUE: `(account_id, first_save_order)`
- `adjustment_amount <> 0`
- `first_save_order > 0`

## 12.4 Create Semantics

CreateBalanceAdjustment：

1. 获取 Account `FOR UPDATE`；
2. 在同一事务中 Query-time 计算 Current Balance；
3. `adjustment = targetBalance - currentBalance`；
4. 如果 `adjustment == 0`：不创建记录；
5. 否则分配新的 Account `first_save_order`；
6. 保存固定 `adjustment_amount`；
7. Commit。

历史或未来 `business_time` 不影响步骤 2 的 Current Balance 计算基准。

## 12.5 Indexes

- `uk_adjustments_account_order(account_id, first_save_order)`
- `idx_adjustments_ledger(account_id, business_time, first_save_order)`

# 13. Balance / Derived Query

不建立 Balance 表。

查询公式：

```text
Current Balance
= accounts.opening_balance
+ SUM(INCOME transaction.amount)
- SUM(EXPENSE transaction.amount)
+ SUM(balance_adjustments.adjustment_amount)
```

规则：

- 所有已保存记录参与；
- 包括未来 Business Record Time；
- 当前查询月份不影响 Current Balance；
- Deleted Transaction / Adjustment 不再存在，因此自然不参与；
- 金额全部使用精确 Decimal。

# 14. Statistics / Derived Read Model

不建立统计持久化表。

## 14.1 Monthly Summary

按指定北京时间自然月：

```text
transaction_count = count(Transaction)
net_income = SUM(Transaction.amount WHERE type=INCOME)
net_expense = SUM(Transaction.amount WHERE type=EXPENSE)
surplus = net_income - net_expense
```

BalanceAdjustment 不参与。

## 14.2 Category Statistics

只从 `transactions` 聚合：

- Transaction 直接关联可记账 Category；
- 一级有 Children 时，通过 Category Tree 汇总 Children；
- 一级汇总与 Children 不重复计入 Overall Total。

## 14.3 Tag Statistics

从：

```text
transactions
JOIN transaction_tags
JOIN tags
```

聚合。

一笔 Transaction 有多个 Tag 时完整计入每个 Tag。

因此 Tag Aggregates 不可相加作为 Overall Total。

无 Tag Transaction 通过 Anti-Join / NOT EXISTS 形成“无标签”派生分组。

# 16. Delete Strategy

v0.1 推荐：

**Hard Delete / 物理删除业务记录**

适用于：

- Transaction；
- BalanceAdjustment。

理由：

- 产品明确不提供回收站 / 恢复；
- 当前没有审计历史或 Event Sourcing 要求；
- Query-time Balance / Statistics 在物理删除后自然撤销影响；
- 模型和查询保持简单。

`transaction_tags` 随 Transaction `ON DELETE CASCADE` 删除。

Tag / Category 本期没有删除 API。

注意：

> Create Operation 的幂等历史由独立 `idempotency_records` 保留，因此业务记录物理删除不会使旧 Operation ID 失效，也不会导致旧创建请求重新创建业务记录。

如果未来出现审计或恢复需求，再重新评估 Soft Delete；当前不因幂等需求引入 Soft Delete。

# 21. Human Review Result / 人工 Review 结论

以下设计已确认：
1. Account Row 在首次完成 Opening Balance 初始化时创建；
2. v0.1 保留 `UNIQUE(accounts.user_id)`；
3. `accounts.last_first_save_order` 作为 Account-scoped monotonic counter；
4. Transaction / BalanceAdjustment 使用 Hard Delete；
5. 幂等历史由独立 `idempotency_records` 保留；
6. Money 使用 `DECIMAL(19,2)`；
7. 统一使用 `utf8mb4 / utf8mb4_0900_ai_ci`；
8. v1.0 多账户方向只记录 Evolution Note，不提前削弱 v0.1 约束。
