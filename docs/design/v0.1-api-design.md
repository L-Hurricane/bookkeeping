# 1. API Principles / API 原则

1. Base Path：

```text
/api/v1
```

2. 认证后的请求使用：

```http
Authorization: Bearer <opaque-token>
```

Token 是不透明随机值，客户端不解析其中内容。

3. API 不接受客户端提供 `userId` 决定数据归属。

User Context 必须来自：

```text
Opaque Token
→ Server Session
→ Trusted User Context
```

4. 金额不使用 JSON Binary Floating Point 作为正式合同。

API Money 使用**十进制字符串**：

```json
"30.00"
"-30.00"
"0.50"
```

5. Business Time 使用带明确 `+08:00` Offset 的 RFC 3339 秒级格式：

```text
2026-09-30T23:59:59+08:00
```

服务端验证并按北京时间业务语义保存。

6. 自然月使用：

```text
YYYY-MM
```

例如：

```text
2026-09
```

7. CreateTransaction / CreateBalanceAdjustment 使用：

```http
Idempotency-Key: <operation-id>
```

8. v0.1 不做分页。

原因：

- 仅个人账户；
- 按单自然月查询；
- 当前无数据量 Driver。

未来出现真实数据量问题再增加 Cursor Pagination。

# 2. Common Headers

## 2.1 Authorization

除 Login 外，业务 API 均要求：

```http
Authorization: Bearer <opaque-token>
```

认证失败：

```text
401 Unauthorized
```

---

## 2.2 Idempotency-Key

用于：

- CreateTransaction；
- CreateBalanceAdjustment。

格式：

```http
Idempotency-Key: <client-generated opaque id>
```

建议客户端每次“新的保存意图”生成新的高随机 Key。

同一个保存意图：

- 用户重复点击；
- 网络超时后重试；

必须复用原 Key。

服务端 Scope：

```text
User + Endpoint Operation Scope + Idempotency-Key
```

---

## 2.3 Request ID

服务端为每个请求建立 Request / Correlation ID。

响应建议返回：

```http
X-Request-Id: <request-id>
```

错误响应同时包含 `requestId`。

# 3. Money Contract

## 3.1 Request

Money 字段必须是字符串。

合法：

```json
"100"
"100.00"
"-30.00"
"0.50"
```

非法：

```json
100.1
0.30000000000000004
"1.234"
```

服务端：

- 最多两位小数；
- 使用 Decimal 解析；
- 规范化后返回两位小数。

## 3.2 Response

统一返回：

```json
"100.00"
"-30.00"
"0.50"
```

这避免微信小程序 JavaScript Number 参与正式金额语义。

---

# 4. Time Contract

## 4.1 Business Record Time

请求：

```json
{
  "businessTime": "2026-09-30T23:59:59+08:00"
}
```

规则：

- 必须精确到秒；
- Offset 必须能解析为北京时间业务语义；
- 服务端内部使用 `Asia/Shanghai` 判断 Calendar Month；
- 不允许早于 Account Creation Time；
- 允许未来时间。

## 4.2 Technical Time

`firstSavedAt`、`updatedAt` 等技术时间不是当前 UI 核心业务字段。

除非客户端确实需要，v0.1 业务 API 不主动暴露这些 Technical Metadata。

## 4.3 Month

查询：

```text
month=2026-09
```

服务端转换为北京时间：

```text
[2026-09-01 00:00:00,
 2026-10-01 00:00:00)
```

# 5. Authentication APIs

## 5.1 Login

```http
POST /api/v1/auth/login
```

### Request

```json
{
  "username": "demo",
  "password": "********"
}
```

### Success

```http
200 OK
```

```json
{
  "token": "<opaque-token>",
  "expiresAt": "2026-10-01T04:00:00Z"
}
```

说明：

- 原始 Token 只在登录成功响应中返回；
- 服务端数据库只保存 Token Hash；
- Session TTL 属于运行配置，不属于产品业务规则。

### Failure

用户名或密码错误：

```http
401 Unauthorized
```

```json
{
  "error": {
    "code": "AUTHENTICATION_FAILED",
    "message": "用户名或密码错误",
    "requestId": "..."
  }
}
```

不要向客户端区分：

- 用户不存在；
- 密码错误。

---

## 5.2 Logout

```http
POST /api/v1/auth/logout
Authorization: Bearer <opaque-token>
```

### Success

```http
204 No Content
```

服务端删除 / 失效当前 Session。

---

## 6.2 Initialize Account

```http
POST /api/v1/accounts/initialize
```

### Request

客户端只提交 Opening Balance：

```json
{
  "openingBalance": "100.00"
}
```

客户端不能指定：

- Account Name；
- Currency；
- User ID。

服务端固定：

```text
name = 微信
currency = CNY
```

并以初始化成功时刻建立 Account Creation Time。

### Success

```http
201 Created
```

```json
{
  "id": 1001,
  "name": "微信",
  "currency": "CNY",
  "openingBalance": "100.00",
  "currentBalance": "100.00",
  "createdTime": "2026-09-01T10:00:00+08:00"
}
```

### Already Initialized

```http
409 Conflict
```

```json
{
  "error": {
    "code": "ACCOUNT_ALREADY_INITIALIZED",
    "message": "资金账户已经初始化",
    "requestId": "..."
  }
}
```

客户端遇到该结果后可重新 `GET /accounts` 获取正式状态。

初始化后不提供修改 Opening Balance API。

# 9. Transaction APIs

## 9.1 Create Transaction

```http
POST /api/v1/accounts/{accountId}/transactions
Idempotency-Key: <operation-id>
```

### Request

```json
{
  "type": "EXPENSE",
  "amount": "30.00",
  "name": "午餐",
  "categoryId": 203,
  "tagIds": [301],
  "businessTime": "2026-09-24T12:30:00+08:00",
  "remark": "工作日午餐"
}
```

规则：

- `type` 必填；
- `amount` 非 0；
- `name` 可 NULL / 空；
- `categoryId` 必须是当前 User 的同 Type 可记账分类；
- `tagIds` 可空数组；
- Tag 必须当前 User、同 Type；
- `businessTime` 不早于 Account Creation Time；
- 未来时间允许并立即影响 Current Balance；
- Transaction + Category Reference + Tag Association Set 在一个 MySQL Transaction 中原子完成。

### Success

```http
201 Created
```

```json
{
  "id": 4001,
  "accountId": 1001,
  "type": "EXPENSE",
  "amount": "30.00",
  "name": "午餐",
  "displayName": "午餐",
  "category": {
    "id": 203,
    "name": "午餐"
  },
  "tags": [
    {
      "id": 301,
      "name": "外卖"
    }
  ],
  "businessTime": "2026-09-24T12:30:00+08:00",
  "remark": "工作日午餐"
}
```

如果 `name` 未填写：

```json
"displayName": "午餐"
```

取 Category Name，但服务端不把 Category Name 回写成 Transaction Name。

---

## 9.2 Idempotent Replay

同 User、同 CreateTransaction Scope、同 `Idempotency-Key`：

### Same Request Hash

不创建第二笔。

推荐：

```http
200 OK
Idempotent-Replay: true
```

返回现有 Transaction 当前可见状态。

原 Transaction 已被删除时，Idempotency Record 仍然保留。同一 Key 与同一原始请求不得重新执行 Create。响应为：

```http
404 Not Found
Idempotent-Replay: true
```

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "资源不存在",
    "requestId": "..."
  }
}
```

### Different Request Hash

```http
409 Conflict
```

```json
{
  "error": {
    "code": "IDEMPOTENCY_CONFLICT",
    "message": "同一个 Idempotency-Key 已用于不同的创建请求",
    "requestId": "..."
  }
}
```


### Success

```http

```

返回与 Create Success 相同的业务字段结构。

```http
404 Not Found
```

---

## 9.4 Update Transaction

```http
PUT /api/v1/accounts/{accountId}/transactions/{transactionId}
```

### Request

**不包含 `type`。**

```json
{
  "amount": "30.00",
  "name": "午餐",
  "categoryId": 203,
  "tagIds": [301],
  "businessTime": "2026-09-24T12:30:00+08:00",
  "remark": "修改后的备注"
}
```

PUT 表达：

> 完整替换当前 Transaction 的全部可编辑字段。

规则：

- `type` 不允许变更；
- First Saved Time 不变；
- First Save Order 不变；
- Category / Tag 必须继续匹配原 Transaction Type；
- 最终 Tag Association Set 与 Transaction 更新原子提交；
- 编辑会按新的 Business Time 改变月份归属和 Ledger 主排序位置。

### Success

```http
200 OK
```

返回更新后的 Transaction。

如果 Request 中出现未知字段 `type`，推荐按严格 Schema：

```http
400 Bad Request
```

`VALIDATION_FAILED`

而不是静默忽略。

---

## 9.5 Delete Transaction

```http
DELETE /api/v1/accounts/{accountId}/transactions/{transactionId}
```

### Success

```http
204 No Content
```

服务端：

- Account Lock；
- 删除 Transaction；
- `transaction_tags` Cascade 删除；
- Balance / Statistics 下次查询自然反映删除结果。

API 不负责“二次确认 UI”。

二次确认属于客户端交互，但服务端 Delete 必须是显式独立请求。

---

# 10. Balance Adjustment APIs

## 10.1 Create Balance Adjustment

```http
POST /api/v1/accounts/{accountId}/balance-adjustments
Idempotency-Key: <operation-id>
```

### Request

客户端提交：

```json
{
  "targetBalance": "60.50",
  "businessTime": "2026-09-30T23:59:59+08:00",
  "remark": "月末核对"
}
```

客户端**不提交可信的 `adjustmentAmount`**。

服务端：

1. 认证并建立 User Context；
2. 获取 Account Row Lock；
3. Query-time 重新计算提交时 Current Balance；
4. `adjustmentAmount = targetBalance - currentBalance`;
5. 如果非 0：
   - 分配 First Save Order；
   - 保存 BalanceAdjustment；
6. 如果为 0：
   - 不创建业务记录；
7. 无论 CREATED / NO_CHANGE，都把结果写入同一事务内的 `idempotency_records`；
8. Commit。

---

## 10.2 Created

```http
201 Created
```

```json
{
  "created": true,
  "currentBalanceBefore": "65.50",
  "targetBalance": "60.50",
  "adjustment": {
    "id": 5001,
    "adjustmentAmount": "-5.00",
    "businessTime": "2026-09-30T23:59:59+08:00",
    "remark": "月末核对"
  },
  "currentBalanceAfter": "60.50"
}
```

---

## 10.3 No Change

如果：

```text
targetBalance == Current Balance at Commit
```

不创建 BalanceAdjustment。

推荐：

```http
200 OK
```

```json
{
  "created": false,
  "reason": "NO_ADJUSTMENT_NEEDED",
  "currentBalance": "60.50",
  "targetBalance": "60.50"
}
```

这不是 Server Error，也不是 Validation Error。

它表示：

> 用户的业务意图已经满足，因此没有产生新的业务记录。

同一 Idempotency-Key 重试时，无论之后账户余额是否已经发生变化，仍重放首次确定的 `NO_ADJUSTMENT_NEEDED` 结果。

---

# 11. Ledger API

## 11.1 Query Monthly Ledger

```http
GET /api/v1/accounts/{accountId}/ledger?month=2026-09
```

### Response

```json
{
  "accountId": 1001,
  "month": "2026-09",
  "currentBalance": "60.50",
  "summary": {
    "transactionCount": 3,
    "netIncome": "0.50",
    "netExpense": "35.00",
    "surplus": "-34.50"
  },
  "items": [
    {
      "kind": "BALANCE_ADJUSTMENT",
      "id": 5001,
      "displayName": "余额调整",
      "amount": "-5.00",
      "businessTime": "2026-09-30T23:59:59+08:00"
    },
    {
      "kind": "TRANSACTION",
      "id": 4003,
      "transactionType": "INCOME",
      "displayName": "利息",
      "amount": "0.50",
      "category": {
        "id": 220,
        "name": "利息"
      },
      "tags": [],
      "businessTime": "2026-09-30T23:58:00+08:00"
    }
  ]
}
```

服务端组合：

```text
Transaction
UNION ALL
BalanceAdjustment
```

排序：

```text
Business Record Time DESC
First Save Order DESC
```

`First Save Order` 不必暴露给客户端。

`currentBalance` 与 `month` 无关，始终表示当前 Account Balance。

`summary` 排除 BalanceAdjustment。

# 13. Error Model

统一结构：

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "请求参数不合法",
    "details": [
      {
        "field": "amount",
        "reason": "MUST_NOT_BE_ZERO"
      }
    ],
    "requestId": "..."
  }
}
```

`details` 可选。

# 14. Error Categories

| HTTP | Code Example | Meaning |
|---:|---|---|
| 400 | `VALIDATION_FAILED` | JSON / 字段格式 / 必填 / 精度错误 |
| 401 | `AUTHENTICATION_FAILED` | Login 失败 |
| 401 | `SESSION_INVALID` | Token 缺失、无效或过期 |
| 403 | `OPERATION_FORBIDDEN` | 已认证但操作本身不允许 |
| 404 | `RESOURCE_NOT_FOUND` | 当前 User Scope 下资源不存在 |
| 409 | `TAG_NAME_CONFLICT` | Tag User Scope 唯一性冲突 |
| 409 | `ACCOUNT_ALREADY_INITIALIZED` | 重复初始化 |
| 409 | `IDEMPOTENCY_CONFLICT` | 同 Key 被用于不同 Request |
| 409 | `BUSINESS_RULE_VIOLATION` | 业务状态冲突，无法按请求执行 |
| 500 | `INTERNAL_ERROR` | 未预期服务端异常 |

## Ownership

资源查询始终带 Trusted User Scope。

对于：

> 资源 ID 存在，但属于其他 User

对外仍返回：

```text
404 RESOURCE_NOT_FOUND
```

避免泄露其他 User 数据是否存在。

内部日志可以记录 Ownership Rejection，但不向客户端泄露。

因此：

- Permission 概念在服务端明确存在；
- 外部 Resource Ownership Failure 与 Not Found 有意合并为安全的 404；
- `403` 保留给“资源属于本人，但当前操作本身不允许”的场景。

# 19. Human Review Result / 人工 Review 结论

以下 API Contract 已确认：
1. Money 使用 JSON Decimal String；
2. BalanceAdjustment `NO_CHANGE` 使用 `200 OK + created=false`；
3. 跨 User Resource 对外统一返回 `404 RESOURCE_NOT_FOUND`；
4. Transaction Edit 使用 `PUT`，请求不包含 `type`；
5. Opaque Token + DB-backed Session 保持不变；
6. CreateTransaction / CreateBalanceAdjustment 使用 `Idempotency-Key`；
7. 客户端只提交 BalanceAdjustment `targetBalance`，服务端计算 `adjustmentAmount`。

当前没有阻塞 Implementation Plan 的 API 问题。
