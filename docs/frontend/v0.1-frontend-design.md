# 记账软件 · Frontend Design Baseline

> 文档状态：**Confirmed / Frontend Design Baseline**
> 目标版本：v0.1 客户端，含已验收的 v0.2 可选分类
> 上游：Product / UI Freeze、Domain Baseline、Architecture Baseline、API Baseline、`docs/changes/v0.2-optional-transaction-category.md`
> 用途：微信小程序前端的架构与交互基线。不写页面实现、接口封装或组件流水账。

v0.1 后端是已验收的业务实现。本文只冻结第一个客户端怎么用它，不改写后端领域或 API。

## Technology

- 客户端是微信原生小程序，语言是 TypeScript。
- 不使用 Taro、uni-app，也不使用 React / Vue 或其他跨端层。
- 不引入大型 UI 组件库。
- 工程需要能做类型检查、lint 和单元测试；微信开发者工具负责导入运行与真机相关验证。

## Architecture

后端是业务 Source of Truth。认证、用户隔离、金额、余额、统计、幂等和持久化都在后端完成。

前端只负责：

- UI State
- Form Draft
- View Model
- Light Cache

前端不复制 Backend Domain Model，不建立 Frontend Local DB，不做 Offline-first，也不引入复杂全局 State Framework。

当前每个用户只有一个资金账户，名称为「微信」，币种为人民币。它是手工记账账户，不连接微信支付或外部账单。

## Navigation

核心页面方向：

- Login
- Account Init
- Account Home
- Transaction Form
- Transaction Detail
- Category Picker
- Tag Picker
- Balance Adjustment
- Statistics Detail

页面按上述方向逐步实现。未进入对应阶段时不预建业务页面空壳。

## Transaction Save Positioning

Create / Edit 保存成功后：

- 返回所属 Account Ledger。
- 切换到该 Transaction 当前 Business Record Time 所属自然月。自然月按北京时间。
- reload Backend Ledger。
- 使用 Transaction ID 定位。
- 最新记录正常位于顶部。
- 历史补录尽量位于屏幕垂直中部。
- 接近列表尾部时，允许受边界限制位于中下部。
- 定位后使用柔和 Highlight，约 2–3 秒平滑消失。

## Uncategorized

v0.2 起，一笔 Transaction 可以没有分类。

- UI 可以显示「未分类」。
- Backend `categoryId = null`。响应在非空 JSON 策略下会省略空的 `category`。
- 不存在特殊 Category Entity，也不把「未分类」种进分类树。
- Statistics 顶层使用 `kind = CATEGORY | UNCATEGORIZED`。`UNCATEGORIZED` 不是任何分类的子节点。
- Uncategorized drill-down 使用 `uncategorizedOnly=true`。`false` 或省略该参数都不启用该过滤，且不能与 `categoryId` 同时使用。

## Display Placeholder

Backend `displayName` 取交易名称，否则取分类名称，否则省略。后端不发明「未分类」作为交易名称。

Name 和 Category 都不存在时：

- UI 显示弱化的「未命名交易」。
- 该文案只存在于前端展示，不写回 Backend。

## Money

- Backend 金额是十进制字符串，响应规范为两位小数。
- 前端不使用 JavaScript floating-point 重新计算权威 Balance 或 Statistics。
- 当前余额、月度统计、分类统计和标签统计以 Backend 派生结果为准。

## Session

登录成功后，前端只把 opaque token 和 `expiresAt` 写入微信小程序本地存储。Token 不解析、不解码。不使用 Refresh Token 或 JWT。

Bootstrap 是小程序声明首页，也是统一业务启动入口。Login 只是未认证状态页面，不是应用首页。微信「返回首页」回到 Bootstrap。App 启动不根据 Session 再跳转。

Bootstrap 只做 Session Gate，不请求 Backend：

- 没有有效 Session，进入 Login。
- 本地 Session 未过期，进入 Account Home。
- 存储内容无法解析、字段缺失，或 `expiresAt` 已到，都视为没有 Session 并清除本地记录。

已登录后的应用主页是 Account Home。登录成功直接进入 Account Home，不再经过 Bootstrap。已登录用户如果停留在 Login，Login 也直接进入 Account Home。

## Account Startup

Account Home 拥有唯一一次启动期 `GET /api/v1/accounts`，随后再读取 Ledger。Bootstrap 不再查询账户，因此不会和 Account Home 各查一次。

- 成功且 `items` 为空：进入 Account Init。这是尚未初始化，不是错误。
- 成功且恰好一个 Account：留在 Account Home，并读取该账户的 Ledger。
- 成功但超过一个 Account：按契约违反处理，不自行挑选。
- 请求失败或响应无法识别：留在 Account Home 的错误状态，可以重新加载。不得把失败当成没有 Account。

Account Init 只提交 Opening Balance 字符串。未输入时按产品默认值 0 提交。名称、币种和用户标识由 Backend 决定。

`POST /api/v1/accounts/initialize` 返回 201 时，响应必须通过 Account 校验。这次校验是初始化成功的权威确认，不把用户输入组装成 Account。通过后进入 Account Home。Account Home 进入后再 `GET /accounts`，不把 201 的 Account 放进全局 Store，也不依赖跨页面内存。当前余额直接显示这次查询返回的 `currentBalance`。

返回 `409 ACCOUNT_ALREADY_INITIALIZED` 时重新 `GET /accounts`。读到唯一 Account 就进入 Account Home。重新查询仍为空或失败时显示错误，不编造 Account。页面重新进入或小程序重启后，同样重新查询。

服务端 401 仍然是认证是否有效的最终依据。本地过期检查只用于少发一次已知失效的请求。

## Authentication Errors

请求必须标明是否需要认证。

- Login 的 401 `AUTHENTICATION_FAILED` 只表示用户名或密码错误。它不清除本地 Session，也不走已登录会话失效处理。
- 已认证请求的 401 清除本地 Session，并 `reLaunch` 到 Login。若当前已经在 Login，不再跳转。

## Logout

`POST /api/v1/auth/logout` 携带 `Authorization: Bearer <opaque-token>`。

- 204：清除本地 Session，回到 Login。
- 401：服务端会话已经无效，同样清除本地 Session，回到 Login。
- 其他网络或服务端失败：保留本地 Session，并向用户显示退出失败。不得把它当成退出成功。

## Account Home Ledger

Account Home 在确认唯一 Account 后读取 `GET /api/v1/accounts/{accountId}/ledger?month=YYYY-MM`。首次月份是当前北京时间自然月，不使用设备时区。切换月份只重读 Ledger，不重读 Account。

当前余额使用 Ledger 响应里的 `currentBalance`，与所选月份无关。月度总计和流水顺序都使用 Backend 返回值，前端不重算、不重排。

旧月份响应不能覆盖当前选中月份。页面卸载或退出开始后，未完成的 Ledger 响应不再更新页面。

本月没有记录时仍显示账户、余额、月份和全 0 的月度总计，并提示“本月暂无记录”。Ledger 失败时保留账户和所选月份，显示失败并允许重试，不把失败当成空流水。

## Create Transaction Design

记一笔表单包含类型、金额、名称、可选分类、多个标签、业务时间和备注。分类可空。标签创建后独立存在，取消或保存失败不回滚标签。

金额是字符串。业务时间是北京时间，精确到秒，格式为 `YYYY-MM-DDTHH:mm:ss+08:00`。未来时间允许。金额符号不改变交易类型。

提交前生成不可变 Snapshot。同一 Snapshot 必须构造出相同的业务请求。`categoryId`、`name`、`remark` 为空时省略，不发送 `null`。`tagIds` 始终发送，并按 id 升序去重。

保存后的目标月份只从 Backend Transaction Response 的 `businessTime` 得出，不从原表单推导。按这个月份回到 Ledger 属于 Phase 0E-4。

### Phase 0E-2

Account Home 在账户已读取后提供「记一笔」。Ledger 仍在加载或加载失败时可以进入；账户未知或正在退出时不可以。页面只接收 `accountId` 和 `accountCreatedTime`。`+08:00` 会做 URL 编码。参数无效时不初始化表单，也不请求分类或标签。

分类和标签按 `EXPENSE` / `INCOME` 分别缓存。切换类型保留金额、名称、业务时间和备注，并清空分类、已选标签和未提交的新标签输入。已成功的缓存直接复用。某一类型的响应可以写入该类型缓存，但不能改写当前另一类型的界面。

分类选择保持在记一笔页面内。未分类对应 `categoryId = null`。没有子分类且 `bookable` 的一级可以直接选择。有子分类的一级只作为分组。可选的是 `bookable` 子分类。分类或标签加载失败只影响对应区域，金额、名称、时间和备注仍可编辑。

标签用 Chip 按 id 多选。新建标签调用 `POST /api/v1/tags`，成功后只把新标签合并进提交类型已有的标签。这不改变该类型列表的加载状态：列表失败仍然失败，并继续提供重新加载。列表失败时，已经在本地的标签仍然显示。较早返回的标签列表按 id 合并，不能覆盖刚创建的标签。

每个创建请求只拥有它开始时的那一次输入。之后切换类型或重新打开输入，旧请求的成功或失败都不能清空、关闭或覆盖新的输入。创建失败记在提交类型自己的输入上，不用一个全局错误挂到另一个类型或另一次输入。

分类选择是页面内的底部浮层，打开后出现在当前视口。取消和保存固定在页面底部。

主表单用一行显示北京时间，例如 `2026-09-26 12:46:06`。内部值仍是 `YYYY-MM-DDTHH:mm:ss+08:00`。点击后在当前页打开编辑层，直接输入日期和时间，并可用现在、今天、昨天。只有确定且校验通过后才一次写入正式交易时间。早于账户创建时间时留在编辑层提示。晚于当前北京时间时，主表单显示弱提示，不二次确认。

页面内取消和导航栏返回都要确认「放弃本次记账？」。继续编辑保留表单。放弃只丢弃未保存的交易表单，不删除已经创建的标签。导航栏返回使用 `wx.enableAlertBeforeUnload`。确认放弃后先关闭该询问，再返回。手势滑动返回不受该接口拦截。

### Phase 0E-3

保存时先做本地校验，再生成新的 `Idempotency-Key`，并把不可变 Snapshot 与这把 Key 固定成一次 `SubmissionAttempt`。之后的请求和重试都使用这份 Attempt，不再从当前表单重建。

`POST /api/v1/accounts/{accountId}/transactions` 返回 201，或同一 Key 的 200 重放，只要 Transaction Response 合法，都视为保存成功。目标月份来自响应里的 `businessTime`。本阶段只记下这个结果，不返回流水，也不定位记录。

明确的 400、403、404，以及非 `IDEMPOTENCY_CONFLICT` 的 409，回到可编辑状态并丢弃 Attempt。下一次保存使用新 Key。网络失败、5xx、已发出后的未知异常，以及 2xx 但响应无法确认，进入未确认状态。重试确认继续使用原来的 Snapshot 和 Key。

`409 IDEMPOTENCY_CONFLICT` 锁定页面，不更换 Key，也不回到可编辑状态。用户需要重新进入记账页面。

保存进行中、结果未确认、冲突和成功时，表单都不能再改。

编辑中取消仍确认「放弃本次记账？」。保存进行中只提示稍候，不离开页面。结果未确认时可以选择继续确认或离开。冲突允许直接离开，不再询问是否放弃未保存内容。成功后的返回见 Phase 0E-4。

### Phase 0E-4

Create Transaction 成功后，用 Backend Response 生成的 `PostSaveResult` 通过页面 EventChannel 交给 Account Home，然后返回。事件只包含 `transactionId` 和 `targetMonth`。201 和同一把 Key 的 200 重放都只交接一次。编辑中取消、结果未确认时离开、以及 `IDEMPOTENCY_CONFLICT` 都不发出这个事件。

Account Home 把目标月份设为 `targetMonth`，并在回到页面后重新 `GET /accounts` 和该月 Ledger。余额、月度总计和流水顺序都只采用这次读取结果。不把 Transaction Response 插进流水，也不在前端重算余额或总计。

定位只匹配 `kind = TRANSACTION` 且 id 相同的记录。列表第一条留在页面顶部。其余记录滚到大约视口中部，由页面滚动自己停在底部。定位成功后该行弱高亮约 2.5 秒。流水加载失败时保留定位意图，重新加载成功后再定位。用户手动切换月份会取消这次定位。Backend 仍是 Source of Truth。

### Phase 0F

流水里的普通交易可以打开详情。详情来自 `GET /accounts/{accountId}/transactions/{transactionId}`，不用流水行代替正式交易。余额调整行仍然只读。

详情页可以进入编辑。交易类型保存后不可修改，请求体也不包含 `type`。金额、名称、分类、标签、业务时间和备注可以修改。编辑中新建的标签独立保存，取消或保存失败都不删除标签。网络结果不确定时，用同一次更新快照重试同一个资源，不新建交易，也不使用 Idempotency-Key。

更新成功后，用响应里的 `businessTime` 得到目标月份，交给 Account Home 已有的保存后定位。如果月份变了，首页读取新的月份并定位同一笔交易。流水顺序仍以重新读取的 Backend 结果为准。

删除需要确认。`204` 表示已删除。详情已经读到的交易如果删除时返回 `404`，也视为已经不存在。网络结果不确定时，对同一个资源重试删除。返回首页后重新读取账户和当前月份流水。余额和总计不在前端改写。

### Phase 0G

账户首页在余额附近提供次级入口「余额调整」，视觉权重低于「记一笔」。进入创建页后重新读取账户，只用这次返回的 Current Balance 做预览。用户输入的是目标余额。预计差额用精确十进制字符串计算，只供确认，文案是「预计增加 / 减少」。目标等于当前预览余额时不提交，并提示无需调整。

正式差额由 Backend 在提交时按锁定后的 Current Balance 计算。请求只带 `targetBalance`、`businessTime` 和可选备注，并使用 Idempotency-Key。`created=true` 的 201 和同一把 Key 的 200 都按创建成功处理，目标月份只取响应里调整记录的 `businessTime`。首页重新读取账户和该月流水，按调整记录的 kind 和 id 定位。`created=false` 且 `NO_ADJUSTMENT_NEEDED` 是已确定的业务结果：不定位、不返回，用响应刷新当前余额，并结束这次 Attempt。之后修改目标会使用新的 Key。结果不确定时用同一快照和同一把 Key 重试。

记录时间沿用已有的业务时间编辑。它可以是过去、现在或未来，但不能早于账户创建时间。它决定流水月份，不表示把某个历史时点的余额改成目标余额。即使选了历史日期，差额仍按提交时的 Current Balance 计算，并立即影响现在的当前余额。

余额调整是独立记录。它没有收入/支出类型、分类、标签，也不能编辑。它改变当前余额，不进入笔数、收入、支出和结余。详情展示固定差额。删除需要确认；`204` 和已经读到详情后的 `404` 都表示记录已经不存在。删除进行中会锁住操作。返回首页后重新读取账户和当前月份流水，不在前端改余额或月度总计。

## Testing Direction

- Unit：纯函数与前端本地规则。
- API Integration：对照 Backend Contract，在接入 HTTP 之后执行。
- WeChat DevTools：页面与基础库行为。
- Real Device Smoke Test：真机关键路径。

Phase 0D 已在 Account Home 接入只读月度 Ledger。Phase 0F 已实现普通交易的详情、编辑和删除。Phase 0G 已实现余额调整的创建、详情和删除。独立 Statistics 页面仍不在当前实现范围内。
