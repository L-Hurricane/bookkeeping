# 记账软件 · Frontend Design Baseline

> 文档状态：**Confirmed / Frontend Design Baseline**
> 目标版本：v0.1 客户端，含已验收的 v0.2 可选分类
> 上游：Product / UI Freeze、Domain Baseline、Architecture Baseline、API Baseline、`docs/changes/v0.2-optional-transaction-category.md`
> 用途：微信小程序前端的架构与交互基线。不写页面实现、接口封装或组件流水账。

v0.1 后端是已验收的业务实现。本文只冻结第一个客户端怎么用它，不改写后端领域或 API。

## Technology

- 客户端是微信原生小程序，语言是 TypeScript。
- 不使用 Taro、uni-app，也不使用 React / Vue 或其他跨端层。
- 不引入大型 UI 组件库。
- 工程需要能做类型检查、lint 和单元测试；微信开发者工具负责导入运行与真机相关验证。

## Architecture

后端是业务 Source of Truth。认证、用户隔离、金额、余额、统计、幂等和持久化都在后端完成。

前端只负责：

- UI State
- Form Draft
- View Model
- Light Cache

前端不复制 Backend Domain Model，不建立 Frontend Local DB，不做 Offline-first，也不引入复杂全局 State Framework。

当前每个用户只有一个资金账户，名称为「微信」，币种为人民币。它是手工记账账户，不连接微信支付或外部账单。

## Navigation

核心页面方向：

- Login
- Account Init
- Account Home
- Transaction Form
- Transaction Detail
- Category Picker
- Tag Picker
- Balance Adjustment
- Statistics Detail

页面按上述方向逐步实现。未进入对应阶段时不预建业务页面空壳。

## Transaction Save Positioning

Create / Edit 保存成功后：

- 返回所属 Account Ledger。
- 切换到该 Transaction 当前 Business Record Time 所属自然月。自然月按北京时间。
- reload Backend Ledger。
- 使用 Transaction ID 定位。
- 最新记录正常位于顶部。
- 历史补录尽量位于屏幕垂直中部。
- 接近列表尾部时，允许受边界限制位于中下部。
- 定位后使用柔和 Highlight，约 2–3 秒平滑消失。

## Uncategorized

v0.2 起，一笔 Transaction 可以没有分类。

- UI 可以显示「未分类」。
- Backend `categoryId = null`。响应在非空 JSON 策略下会省略空的 `category`。
- 不存在特殊 Category Entity，也不把「未分类」种进分类树。
- Statistics 顶层使用 `kind = CATEGORY | UNCATEGORIZED`。`UNCATEGORIZED` 不是任何分类的子节点。
- Uncategorized drill-down 使用 `uncategorizedOnly=true`。`false` 或省略该参数都不启用该过滤，且不能与 `categoryId` 同时使用。

## Display Placeholder

Backend `displayName` 取交易名称，否则取分类名称，否则省略。后端不发明「未分类」作为交易名称。

Name 和 Category 都不存在时：

- UI 显示弱化的「未命名交易」。
- 该文案只存在于前端展示，不写回 Backend。

## Money

- Backend 金额是十进制字符串，响应规范为两位小数。
- 前端不使用 JavaScript floating-point 重新计算权威 Balance 或 Statistics。
- 当前余额、月度统计、分类统计和标签统计以 Backend 派生结果为准。

## Session

登录成功后，前端只把 opaque token 和 `expiresAt` 写入微信小程序本地存储。Token 不解析、不解码。不使用 Refresh Token 或 JWT。

应用启动时只判断本地 Session：

- 没有有效 Session，进入 Login。
- 本地 Session 未过期，进入 Bootstrap。Account Query 不放在 App 启动里。
- 存储内容无法解析、字段缺失，或 `expiresAt` 已到，都视为没有 Session 并清除本地记录。

## Account Startup

Bootstrap 是已登录后的业务启动页。它请求 `GET /api/v1/accounts`：

- 成功且 `items` 为空：进入 Account Init。这是尚未初始化，不是错误。
- 成功且恰好一个 Account：进入 Account Home。
- 成功但超过一个 Account：按契约违反处理，不自行挑选。
- 请求失败或响应无法识别：留在 Bootstrap 的错误状态，可以重新加载。不得把失败当成没有 Account。

Account Init 只提交 Opening Balance 字符串。未输入时按产品默认值 0 提交。名称、币种和用户标识由 Backend 决定。

`POST /api/v1/accounts/initialize` 返回 201 时，响应必须通过 Account 校验。这次校验是初始化成功的权威确认，不把用户输入组装成 Account。通过后进入 Account Home。Account Home 进入后再 `GET /accounts`，不把 201 的 Account 放进全局 Store，也不依赖跨页面内存。当前余额直接显示这次查询返回的 `currentBalance`。

返回 `409 ACCOUNT_ALREADY_INITIALIZED` 时重新 `GET /accounts`。读到唯一 Account 就进入 Account Home。重新查询仍为空或失败时显示错误，不编造 Account。页面重新进入或小程序重启后，同样重新查询。

服务端 401 仍然是认证是否有效的最终依据。本地过期检查只用于少发一次已知失效的请求。

## Authentication Errors

请求必须标明是否需要认证。

- Login 的 401 `AUTHENTICATION_FAILED` 只表示用户名或密码错误。它不清除本地 Session，也不走已登录会话失效处理。
- 已认证请求的 401 清除本地 Session，并 `reLaunch` 到 Login。若当前已经在 Login，不再跳转。

## Logout

`POST /api/v1/auth/logout` 携带 `Authorization: Bearer <opaque-token>`。

- 204：清除本地 Session，回到 Login。
- 401：服务端会话已经无效，同样清除本地 Session，回到 Login。
- 其他网络或服务端失败：保留本地 Session，并向用户显示退出失败。不得把它当成退出成功。

## Testing Direction

- Unit：纯函数与前端本地规则。
- API Integration：对照 Backend Contract，在接入 HTTP 之后执行。
- WeChat DevTools：页面与基础库行为。
- Real Device Smoke Test：真机关键路径。

Phase 0C 已接入 Account Query、首次初始化和 Account Home。Ledger 及后续业务页面仍不在当前实现范围内。
