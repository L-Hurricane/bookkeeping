## 可直接复用

这些能力已在源码或已批准文档中，D01 不必重做：

- 表头 12 列：账户、转账、描述、交易对方、分类、日期、时间、备注、金额、货币、支票号码、标签。实现在 LocalTrial 分支 `localtrial/lt01-t02` 的 `MoneyWizSnapshotImport`。
- 符号修复 `e84974712227385d82d47a5d1fa17721a8b2d472` 已在该分支。有分类时方向取分类路径：收入保留源金额，支出取反。无分类历史行按源符号：负数记正支出，正数记正收入。这与当前「负收入仍为收入、负支出仍为支出」一致。报告行是 `amount_sign_meaning=HISTORICAL_EMPTY_CATEGORY_NEGATIVE_EXPENSE_POSITIVE_INCOME`。
- 分类和标签映射可复用：`category.` 路径、`category_separator=/`、`tag_separator=;`。显式映射优先。
- 非空账本拒绝：`LEDGER_NOT_EMPTY`。清空只删除该用户的流水、转账、调整、分类、标签和分析行；可以选择删除账户。它不知道 `account_groups`。
- 已批准的结构 SQL 就是仓库里的 V19、V20。V19 SHA-256 `962e9d9960b71576ae73c4dfbf984f84e730033dfaa143cd0ec7282d48d30218`。V20 SHA-256 `d045172081fd87dd854c5461d784b778b9bfa64f46be19753277deb8a8064691`。个人库升级没有另写一套 SQL 的必要，但把它们应用到个人库仍未批准。

## 不能直接复用

- 转账名称。配对草稿的 `entryName` 为空，定位符是 `L{low}+L{high}`。`INSERT INTO transfers` 不写 `name`。历史「描述」不会进入 `transfers.name`。
- 分组和组内排序。导入插入账户时不写 `group_id`、`display_order`。整库重建会丢掉这两项，除非先把它们导出，重建后再按账户名贴回去。
- 增量合并。批次身份是整份 CSV 的 SHA。没有按行增量，也没有「保留目标库后补手工账」的合并。
- 个人库当前 Flyway 版本。本轮禁止读取该库，所以实际停在 V18 还是已经有人升过，仍是未知。LocalTrial 工具所在分支没有 V19/V20。

## 重建时的处理选择

一次性重建意味着旧试用账本可以被替换。后补手工账、分组和排序不会自动留下来。执行前只能二选一，并由负责人选定：

1. 重建前导出账户名、分组、组内顺序和目标库独有记录的清单；导入后只恢复分组和顺序，不把旧流水叠回去。
2. 明确放弃这些本地事实，只保留新快照导入的结果。

两种都还没有编码。默认不能悄悄选第 2 种。

## 核账方法

真实 CSV 的固定 SHA、行数和账户映射本轮没有，因为没有读取真实文件。下次获准读取之后，核对应固定为：

- 文件 SHA-256，以及去掉表头后的数据行数。
- 每个源账户名对应一个目标账户，不按名称静默合并同名账户。
- 每个账户用当前余额公式核对：起始金额 + 收入金额 − 支出金额 + 余额调整 + 转入 − 转出。负收入和负支出保持原类型。
- 转账两侧各算一次，金额绝对值相同，业务时间可以不同。
- 分类路径和标签按已确认的映射表核对，不在导入时发明新的同级排序。

审批记录里的截止日期仍是 2026-11-01；若快照晚于该日，源和目标之间新产生的事实都要进这张差异表。

## 最短演练与 STOP

1. 先在授权合成库用已有虚构夹具走一遍「空账本 → V19/V20 已存在 → 导入 → 按上面的余额公式核对 → 丢弃」。不读真实 CSV。
2. 夹具通过后，才申请读取一份指定 SHA 的真实快照，并在可舍弃库上重建。
3. STOP：个人库 Flyway 版本未知仍去执行迁移；SQL 与已批准 V19/V20 不一致；符号或转账名称结果和核账公式不一致；要保留的手工账还没有清单；目标库不是本次点名的可舍弃库。
