## 1. 已核对事实

`transactions` 没有与「交易对方」同义的列。`V6__create_transactions.sql` 的可空文本是 `name` 与 `remark`。`V10__nullable_transaction_category.sql` 把 `category_id` 改为可空。当前创建哈希在 `TransactionRequestHash`，字段依次是账户、类型、金额、分类、标签、业务时间、名称、备注，没有版本前缀。

`transfers.name` 是转账名称。测试里的 counterparty 指转账另一侧账户，不是支出文本。

因此 C11 需要新列。下面的 DDL 只作为批准文本。本轮不创建该文件，不执行它。

## 2. 拟批准的正式 DDL

下一迁移文件只能是 `V21__transaction_counterparty_name.sql`：

```sql
ALTER TABLE transactions
    ADD COLUMN counterparty_name VARCHAR(255) NULL,
    ALGORITHM=INSTANT;
```

- 只加这一可空列。不加索引，不加 CHECK，不做历史回填。CHECK 可能使这条 ALTER 离开 INSTANT。
- 这条 DDL 没有 UPDATE。旧行迁移后仍是 NULL。
- `foreign_key_checks` 保持开启。禁止 `Flyway.clean()`。
- 若实测不是 INSTANT，STOP。不在失败后改写已执行环境里的 V21 充作热修，也不自行换成 COPY。

## 3. 应用与 API

隔离环境中的实施批准之后，应用层才可以改代码：

- trim。空串和纯空白存 NULL。最长 255 个字符，超出拒绝。
- 仅普通支出可新建、修改、用空值清空。
- 收入上的非空值返回 400，不写入，不静默丢弃。转账和余额调整不接收该字段。
- 详情、创建和编辑响应带上该字段。流水查询与名称搜索不选它。余额、分类、标签、统计 SQL 不读它。
- Jackson 省略 null 时，客户端把缺字段当作空。空不是交易名称，也不回填备注。

## 4. 幂等：旧哈希与新哈希的选择路径

不修改历史 `idempotency_records.request_hash`。

规范化对方：trim；NULL、空串和纯空白在哈希中都写成空串。超长请求在计算哈希前拒绝。

两条哈希：

- 旧哈希 H1：无前缀。顺序是账户、类型、金额、分类、标签个数与各标签、业务时间、名称、备注。与当前 `TransactionRequestHash` 一致。
- 新哈希 H2：固定前缀 `transaction-create-v2`，然后是与 H1 相同的八字段，最后是规范化对方。前缀与转账 `transfer-create-v2` 不同，不能复用转账哈希。

创建请求按下面的路径选择，不能只比较其中一条：

1. 同时算出 H1 和 H2。
2. 按用户、`CREATE_TRANSACTION` 和 Idempotency-Key 查找。
3. 没有记录：保存 H2 并创建。不把 H1 写入新记录。
4. 已有记录且存储值等于 H2：重放。
5. 已有记录且存储值等于 H1，并且本次对方为空：重放。不改写存储哈希。
6. 其余情况，包括旧 Key 带上非空对方、新 Key 的对方或其他已哈希字段变化：409。不写交易。

| 请求 | 选择路径 | 结果 |
|---|---|---|
| 无记录的新创建 | 写入 H2 | 创建 |
| 已存 H2，内容相同 | H2 命中 | 重放 |
| 已存 H2，对方或任一已哈希字段变化 | H2 不命中，也不回退到 H1 | 409 |
| 已存 H1，对方为空，八字段一致 | H1 兼容分支 | 重放，存储哈希仍是 H1 |
| 已存 H1，对方非空 | H1 兼容分支拒绝 | 409 |
| 不同 Key | 新记录走 H2 | 按普通创建规则各写一条 |
| 创建后的编辑或清空 | 不进入创建哈希 | 普通 PUT。重放原创建请求只返回当前记录，不把对方写回旧值 |
| 创建的资源已删除后，再用旧 Key | 已有删除事实 | 不创建第二条 |

编辑不是创建。收入拒绝发生在哈希复用之前，不把拒绝写成一次成功的幂等结果。

对应测试必须分开覆盖 H1 分支和 H2 分支：H2 重放、H2 冲突、H1 加空对方重放且哈希不变、H1 加非空对方 409。断言带对方的新请求不会落入旧哈希，旧的空对方请求也不会被当成 H2。

## 5. 合成迁移与合成恢复演练

正式 Schema/DDL 与 Stage Plan 都获批后，才可以在已授权隔离环境创建 V21 文件并验证。此授权只覆盖合成数据。它不授权个人正式库执行。

合成测试使用 `bookkeeping_test`，或另一套已经授权、且不含个人账务的合成库：

- 空库按 V1–V21 迁完，`counterparty_name` 可空，旧行没有被 UPDATE。
- 支出写入、再次编辑、用空值清空。
- 收入携带非空对方被拒绝，且没有新行。
- 旧行只编辑其他字段时，该列仍是 NULL。
- 第 4 节两条选择路径的重放与 409。
- 搜索和月汇总不因该列变化。
- 其他用户读不到这条对方文本。
- 合成恢复只演练合成库自己的备份：停写、备份、执行 V21、失败后用这份合成备份恢复，并把演练进程指回旧构建。备份里没有个人账务。

不连接个人库。不读取个人备份、凭据或 Excel。不把个人真实备份恢复到 `bookkeeping`、`bookkeeping_test`、`bookkeeping_migration_test` 或任何开发库、测试库。不跑会清空 `bookkeeping_migration_test` 的 `MigrationIntegrationTest`，除非另有批准。合成通过不是个人库已升级。

## 6. 与个人正式库执行分离

个人正式库上的停服、备份、Flyway 和恢复不在本次 Schema 批准之内。以后若要执行，必须另有专项批准，由负责人在本人环境操作。Cursor 不接触个人数据、凭据或备份。

若将来需要验证一份个人真实备份能够恢复，也必须另行专项批准，由负责人在独立私人环境执行。该验证不进入开发库或测试库，Cursor 不接触该数据、凭据或备份。

## 7. 拟批准的恢复方案

下面是个人正式库将来升级失败时的恢复方案。它现在是拟批准文本，不是已经批准的回滚，也不是本轮要执行的步骤。恢复手段是旧代码与整库备份一起恢复，不是 `DROP COLUMN`。

1. 停服。停止个人账本后端，确认端口不再接受请求。
2. 停止写入。确认没有导入、第二个进程或待执行任务会写该库。
3. 负责人手动备份。负责人本人从私有配置确认库名，并用现有 Bootstrap 的 `mysqldump` 做一致性逻辑备份：`--single-transaction --routines --events --triggers`，包含 `flyway_schema_history`。文件放在负责人的私人目录。记录时间、字节数和 SHA-256。库名、口令、JDBC URL 和备份内容不写入仓库，不交给 Cursor。
4. 校验旧制品。记下升级前后端制品和小程序制品的可核验 SHA，并确认两份制品仍可取回。同时记下数据库里的 Flyway 历史最高版本。
5. 升级。只在第 3 步和第 4 步都核对完成后，由负责人启动含已批准 V21 的新后端。迁移后只读核对 Flyway 版本、列可空，以及抽样旧行仍为 NULL。同一次操作不回填历史对方。
6. 失败后的联合恢复。停止新服务。用第 3 步的整库备份恢复个人库，核对 Flyway 历史回到第 4 步记下的版本。同时把后端和小程序切回第 4 步的旧制品。只恢复数据库，或只退回代码，都不算恢复完成。完成后再决定是否重试。

INSTANT 加列若在提交前失败，表结构应保持加列前。仍然走第 6 步，不改写 V21，不禁用外键检查，不执行 `Flyway.clean()`。

## 8. 历史回填专项

历史回填不写进 V21，也不随 Schema 批准或 Stage 批准生效。

待另案授权的顺序仍是：不清空正式交易，不重新导入；账户＋描述＋业务时间优先；歧义时加分类、金额和类型；只更新一对一的支出；先给负责人看匹配报告。报告不是写入。执行人是负责人本人。执行前必须已经有批准的 V21，并且第 7 步的备份已经完成。Cursor 不读取 Excel，不连接个人库，不生成生产匹配报告，不执行 UPDATE。
