## 1. Stage 定义

**S1：多资金账户基础与普通交易跨账户记账。** 交付可独立验证的产品增量：同一 User 可以创建并使用至少两个资金账户，普通/信用类型可区分，单笔收支可从 A 改归属到 B，起始金额和余额调整保持派生余额正确，已有单账户数据不丢失。重用已有交易 CRUD/搜索、分类 0/1、标签和页面，不重做已关闭 v0.3 / 已并入主干的日期时间 POC。

**本 Stage 不包含**：转账业务、账户归档/永久删除、完整三级分类/标签树、全账本历史净值、年度 AI 报告、生产部署与正式公众运营。上述为 v1.0 后续 Stage 的保留需求，**不是从 PRD 删除**。

**T02 已获批准的核心架构路线（保留历史原意）**：延续 Spring Boot + MySQL + 小程序现有结构、现有 `Account` ID 及关联；通过版本化迁移放开 `accounts.user_id` 单账户约束，并增补账户名称、类型/状态与名称唯一规则；余额继续派生。若真实 schema 使该方案需要重建账户 ID、批量破坏性迁移或跨服务拆分，则立即暂停并提交架构决策，不在本任务中擅自扩大范围。

**数据安全原则**：只在授权隔离工作区和测试库中修改和测试；真实个人数据、生产库及不可逆删除不得碰触。已有业务代码必须保留 Git 恢复点。

## 2. 交付验收标准（Stage Gate）

1. 用户 U 可创建账户 A（普通）和 B（信用）；账户同一用户内正常+归档名称不重名，不同用户可重名；普通负余额提醒而允许记账，信用负余额不误警告。
2. 现有单账户数据迁移后账户 ID、交易 ID、余额调整固定差额及当前派生余额稳定；隔离测试库中的迁移正向/失败用例 PASS，不能默认生产直接可迁移。
3. 新建交易选择正常账户、只有一个可选账户时允许默认选中；编辑跨账户保持交易 ID、类型、首次保存序与标签关联；A/B 余额相应增减；保存失败无部分迁移。
4. 交易与余额调整接受账户创建前业务时间且当前账面余额立即计算已保存的未来业务记录，历史时间统计按业务时间截止；变更不使既有排序/分类/标签/搜索回归。
5. 小程序入口、账户列表/选择、交易编辑保存返回所属账户的行为符合 UI Freeze；金额正红负绿，负数提醒不误导。
6. `mvnw test`、`npm test`、`npm run typecheck`、`npm run lint` 等适用命令按既有工程路径执行并留存日志；隔离测试库，不运行未获批准的生产迁移、微信上线或真实模型调用。
7. **独立 Supervisor** 复核范围、迁移、权限隔离与事务一致性，未确认关键数据正确性不得 PASS。**在本 v0.3 获批后**，还须核实已有账户级 AI 月度分析的 CURRENT、STALE、生成协调在同一用户的不同账户之间完全隔离，P0/P1 关闭后才可 T07 PASS。
8. **Stage 人工验收：需要**。自动测试与独立审核 PASS 后，由负责人在微信开发者工具/真机对新增多账户场景做一次人工业务验收，方可关闭 S1；不自动授权 S2。

### 3.1 S1-T07R：现有账户级 AI 隔离纠偏（已由独立批准索引正式批准于 v0.3）

**证据和触发条件：** T06 自动化验证 PASS；T07 独立 Supervisor 基于 `AnalysisContextFingerprint`、`MonthlyAnalysisService`、`JdbcAnalysisGenerationStore`、V11 唯一键发现 P1：相同用户不同账户可能复用 CURRENT/IN_PROGRESS；`findLatest(userId, month)` 还可能把 A 的历史报告作为 B 的 STALE。T07 当前 **BLOCKED**，不等于此阶段其他代码失败。完整证据见 `bookkeeping-s1-t07-evidence-review-v0.1.md`。

**最小修复边界与技术约束：**

1. 保持现行账户级 API `/api/v1/accounts/{accountId}/monthly-analysis`、账户账务事实构造、报告内容及调用限额规则不变；**不**提前实现正式 v1.0 AI-01 全账本月/年分析（S5）、模型接入重构或任意账户组合分析。
2. **优先保持原 `AnalysisContextFingerprint` 对事实的纯内容散列语义**，在分析记录持久化、CURRENT/STALE 查询与 `IN_PROGRESS` 协调层新增 `accountId` 作用域，不再以 `(userId, month, fingerprint)` 跨账户共享记录；`findLatest` 必须限定账户。
3. 若现有持久化表确实无法正确区分账户，仅允许一个**新增且可独立测试的 V14 Flyway 迁移**：增加账户归属、建立按用户+账户+月份+指纹的约束/索引，并处理与旧唯一键的兼容；不得修改 V1～V13 或现有账务表、交易、余额、权限模型。先调查具体 V11 表结构、FK 及历史行，再定 DDL。
4. **既有报告迁移策略**：不得将无法证明原账户归属的历史分析快照猜测分配到账户，也不得删除；保留历史行、阻止其跨账户被错误读取。若旧报告无法安全归属，允许其在账户级 UI 中暂时不显示，需要用户重新触发生成；**这项可见性变化构成本 v0.3 需要负责人了解和批准的影响**。如发现必须清除数据、不可逆改迁、改变既有业务限额或访问真实数据库，立即停止并提交单独审批。
5. 仅修改 AI 分析的必要领域/服务/存储/控制器关联代码、迁移、新增集成/负向测试和实施文档；**本 v0.4 审阅建议唯一增加 §3.2 的 BootstrapIntegrationTest 迁移数量断言适配**；不修改已完成的 S1 账户、交易、小程序 UI，也不触发 T08、S2 或 S5 业务范围。
6. 测试验收必须包含：同用户 A/B 同月同内容时互不 REUSED、互不 IN_PROGRESS；A/B 不同内容时互不显示对方 STALE；账户内 CURRENT/STALE、重复请求与并发协调语义不退化；跨用户访问隔离；旧数据/迁移在隔离测试库可验证；前后端现有回归 PASS。不得对真实用户、正式库或未专门批准的库执行 `Flyway.clean()`。
