## 1. 业务目标与范围

**S3 目标**：在现有记账软件、账户/流水和资金计算基础上，交付符合正式 PRD CT-01～CT-10 的**分类 Category 与标签 Tag 的完整独立生命周期**，提供微信小程序可实际使用的管理与交易选择交互，不损伤历史流水及现有金额、统计事实。

### 必须交付

1. **分类**：每用户收入/支出两个命名空间、最多三级树；叶子节点（任意层级均可）可选，交易分类可为空；同一用户同一收支类型跨层级名称唯一，收入和支出允许同名；创建、改名、调整父节点、删除叶子节点。
2. **分类操作限制**：防止循环/超深/跨收支类型移动；节点有直接交易关联时不得新增子节点，也不得通过移动使其成为非叶子；目标父节点直接关联交易时不得挂入子节点；改动结构不改历史交易指向的分类 ID。
3. **分类删除**：仅允许删除无子节点分类；删除前告知直接关联交易数量、影响并确认。原交易变为“未分类”，交易本身及账户/金额/时间/其他标签均不变；删除和解除关联事务原子。
4. **标签**：不区分收入/支出，允许最多三级树和同用户跨全部层级全局名称唯一；任意级标签均可显式关联交易，父子可同时显式关联，多选/取消/再次编辑仍保留实际选择；创建、改名、移动、删除无子节点标签。
5. **标签操作限制**：无循环/超深限制被违反；标签移动不修改原交易直接标签集合；父子关系**不隐式添加交易关联**，目标父标签即使有直接交易关联仍允许子节点；删除叶子标签仅删除该标签直接关联，不删除交易或其他标签关系，删除与关联清理原子。
6. **历史解释**：层级改变后，历史交易按照当前树组织与显示，不做历史版本树查询，不迁移/重写交易事实；保留原交易 ID 与已有财务金额语义。
7. **小程序**：沿现有视觉规范增加分类/标签的实际管理与选择入口，提供必要确认、失败反馈和树层级展示；保持交易点击直接进入可编辑表单、金额正红负绿和已有转账/归档交互。未冻结的管理页细节在 Stage 范围内由组长确定，但不能改变 UI Freeze 主导航或扩展产品范围。
8. **兼容**：已有交易、现有两级固定分类、已有标签及交易标签关联不丢失；现有普通交易、归档账户、转账、统计/AI 既有接口不因 S3 引入不可接受回归。涉及现有统计树形语义，仅保证 S3 必需的数据正确性与现有功能兼容；完整层级统计与全账本统计留给 ST Stage。

## 4. Stage 质量与验收标准

**后端业务不变量（S3 必须）**

- 分类：可从第 1/2/3 级叶子选择；有直接交易关联的分类不能变非叶子；不存在环、超三级、跨收支类型移动；收入类内部跨层级同名拒绝，支出类内部同名拒绝，收入与支出可同名。
- 标签：全用户跨树层级同名拒绝、不分交易收支类型；可显式关联任何层级；父子双选不自动增补、解除或改变其他选择；结构移动不改变交易 ID/标签直接关联集合。
- 删除：有子节点均拒绝；叶子分类被关联时删除后交易仍在且分类为空；叶子标签删除后仅目标标签关联移除；删除及解除关联同事务；无跨用户访问/变更。
- 已有交易与余额：交易金额、账户、时间、首次保存顺序和当前派生余额不因分类/标签维护变化；S1/S2 归档、转账与余额调整不回归。
- 兼容：既有数据、主表 ID、交易-标签关联、分类/标签展示可读；旧数据与正式唯一约束冲突的处理必须有有来源证据和批准方案；数据库迁移失败不能部分破坏业务。

**微信小程序 UAT 重点（由负责人补充体验，不承担全量手工测试）**

1. 创建三级收入分类和三级支出分类；同类跨层级重名被拒绝，收入与支出同名允许；把有直接交易关联的分类尝试加子级/将其作为父级，系统拒绝。
2. 交易选择二级叶子并保存；将分类移动到合法的新父级，历史交易仍展示原节点；删除关联叶子后交易仍存在，显示“未分类”，账户余额不变。
3. 创建三级标签，在收入和支出交易中均能选择同一标签；显式同时选父与子，保存后重新编辑均能看到两项；移动树位置后显式关联不变。
4. 删除有子节点标签被拒绝；删除已关联的叶子标签前提示影响，确认后交易依旧存在且其他标签选择不变。
5. 错误提示、取消、返回、重新进入的行为合理；不额外要求人工重新验证全部 S1/S2 路径。

**测试组织与效率**：一个 Coding Agent 串行推进 T01～T05，自测后按依赖连续工作；T06 仅一次必要集中独立 Testing + Supervisor。若出现实证 P0/P1、专项 DB 安全风险等，按治理允许有限的提前定向复核，不额外增设全量 Gate。最终 T07 为本 Stage 唯一强制产品人工验收里程碑；不附带流程试点验收。
