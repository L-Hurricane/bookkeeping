## 4. C11 Schema 候选（NOT APPROVED）

下一迁移文件只能是 `V21__transaction_counterparty_name.sql`。V19 已是转账名称。不修改已执行的 V1–V20。

候选 DDL，仅作批准文本，不是本轮要运行的脚本：

```sql
ALTER TABLE transactions
    ADD COLUMN counterparty_name VARCHAR(255) NULL,
    ALGORITHM=INSTANT;
```

规则：

- 只加这一可空列，不加索引，不加 CHECK。CHECK 可能把这条 ALTER 从 INSTANT 变成 COPY，个人库上的锁风险另批。
- 应用层：trim；空串和纯空白存 NULL；最长 255。收入上的非空值返回 400，不写入。支出可新建、修改、用空值清空。
- V21 候选本身只有加列，没有 UPDATE。旧行在迁移后仍是 NULL。历史回填不写进这条 DDL，见第 4.1 节。
- 余额、分类、标签、统计 SQL 不读该列。
- 详情和创建、编辑响应带上该字段。流水查询与名称搜索不选它。Jackson 省略 null 时，客户端把缺字段当作空。
- 幂等创建沿用转账 v1/v2：新请求哈希增加前缀 `transaction-create-v2` 和对方文本。已存的旧哈希只在对方为空时仍可重放；同一旧 Key 改带对方则 409。编辑不是创建，清空用普通 PUT。
- 合成测试只使用 `bookkeeping_test`：支出写入、清空、收入拒绝、旧行 NULL 再编辑其他字段后仍为 NULL、幂等重放与冲突、搜索和月汇总不因该列变化、跨用户不可读。不使用个人库，不跑会清空 `bookkeeping_migration_test` 的 `MigrationIntegrationTest`，除非另有批准。

`foreign_key_checks` 保持开启。禁止 `Flyway.clean()`。

### 4.1 历史回填（待实施，未授权）

组长已把第 3、4 节的字段设计接受为候选。下面只记录以后如何把 Excel 里的「交易对方」写到已有支出上。它不是本轮授权，也不批准 V21。

1. 不清空正式交易，不重新导入，不改金额、分类、名称、备注、时间和账户。
2. Excel「描述」与数据库 `transactions.name` 对应。首选匹配键是账户、描述、业务时间。
3. 该键命中多笔时，再使用分类、金额和交易类型分辨。类型必须是支出。
4. 仅当结果是一对一的唯一支出交易时，才允许把「交易对方」写入 `counterparty_name`。无匹配、多匹配、收入、转账和余额调整都不写。
5. 先生成匹配报告，列出可写、歧义和未匹配。报告不是写入。
6. 负责人审阅报告并专项批准后，由负责人在本机执行生产回填。执行前仍要先有已批准的 V21，并完成第 5 节的个人库备份。

在那两项批准下来之前，不读取正式 Excel，不连接个人库，不生成生产匹配报告，不执行 UPDATE。

## 5. 个人库备份与恢复（方案，未授权执行）

编码和测试都不得连接个人账本。下面的步骤只在负责人以后专项批准「对个人库执行 V21」时，由负责人在本机执行。

1. 从本机私有配置确认个人库库名。库名、口令和 JDBC URL 不写入仓库、不写入回执。
2. 用现有 Bootstrap 的 `mysqldump`，对该库做一次一致性逻辑备份：`--single-transaction --routines --events --triggers`，包含 `flyway_schema_history`。文件放在仓库外。记录备份时间、字节数和 SHA-256，记录本身也不进 Git。
3. 恢复演练不是本文件的授权。若要证明备份可恢复，只能在另行批准后，把该备份恢复进已经存在的 `bookkeeping_migration_test`。这会把个人账务复制进迁移库，所以必须单独点头。不得恢复进 `bookkeeping` 或 `bookkeeping_test`，不得为此新建数据库。

5. INSTANT 加列若在提交前失败，表结构应保持加列前。仍以备份为恢复手段，不在失败后改写 V21 文件充作热修。
