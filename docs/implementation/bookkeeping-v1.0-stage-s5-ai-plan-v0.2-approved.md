## 1. 业务目标、边界和完成定义

**目标**：交付小程序内可真实发起、查看并持久保存的**全账本自然月和自然年 AI 分析**。覆盖所有未永久删除账户（包括归档账户），并保证账务数字完全由服务端确定性计算，AI 只提供解释和变化观察。S5 是可独立验收的一个 Stage，不等于整个 v1.0 发布。

**必须覆盖（PRD AI-01～AI-07）**：

1. **AI-01**：范围始终是当前用户整个账本，包含归档账户；不提供自定义账户组合、跨用户访问或自由问答；永久删除账户不纳入新的报告。
2. **AI-02**：用户只能选一个北京时间自然月或自然年，格式分别为 `YYYY-MM` / `YYYY`；不支持季报或任意区间。
3. **AI-03**：仅主动发起生成，不建自动推送、定时任务或 Agent 平台。
4. **AI-04**：沿用单用户每天最多 3 次实际外部模型调用；历史报告查看不消耗额度；配额预留、调用失败、并发与重试不可导致多扣、多调或越界。
5. **AI-05**：复用 S4 确定性统计，聚合账本净值、收入、支出、分类、标签；标签重叠不可简单求和，报告中的数字必须能与源统计口径核对。
6. **AI-06**：报告显示期间净值变化、收支结构、重要分类与标签，以及有限且有依据的同比／环比观察；避免假定“完整家庭资产”、凭空投资建议或消费道德评价。
7. **AI-07**：成功快照持久化、反复查看不重新调用；历史交易变化不会静默改写已生成内容；需要用户明确触发才重新生成且仍计入外部调用限额；对模型仅发送最少必要的统计汇总，不默认上传原始敏感备注或身份信息。

**保留并兼容既有能力**：既有单账户自然月分析的历史数据和读取路径、生成协调／租约和 fencing token、原有单账户调用额度、快照只插入、旧应用 SQL 兼容。**不能把 `account_id IS NULL` 自动解释成 LEDGER**；需依据 `report_scope`，`LEGACY` 行保持独立语义。

**本 Stage 不做**：修改冻结统计 UI 和统计使用逻辑、MoneyWiz 对比、全站底部导航统一、手机号／注销、报表自动推送、AI 问答／投资建议、新模型供应商及基础设施、全面历史归档与逻辑删除平台、外部真实财务数据导入、生产发布；不重新审查 S1～S4 核心 ER。

## 2. 账户永久删除后的历史全账本 AI 报告：方案 B 已获独立批准

**现有冻结文档未明确这一行为**。AC-07 要求用户不可再访问删除账户的普通业务源记录；AI-07 要求生成快照历史内容不被交易修改悄然重写。V18 `LEDGER` 报告的 `account_id=NULL`，现有账户删除 SQL 按具体 `account_id` 清理，**不会自动处理全账本报告**。所以**不能直接凭技术缺省决定**其用户可见性。

- **正式采用方案 B（APPROVED）**：用户永久删除任一账户后，已保存的该用户所有 **LEDGER 月报／年报**均失去用户可读性（可由受控事务删除相关业务可见快照和生成协调行实现，具体实现不预判）。账户删除影响预览明确提示。此前已消耗的 AI 模型额度不退回；系统级短期故障恢复可沿已有备份制度另议，不因此默认永久保留用户敏感报告。普通交易的日常修改仍不影响已生成快照的历史正文。
- **未采用的备选方案 A**：继续允许用户阅读旧全账本报告，并清晰标明“生成时的历史快照，可能包含已永久删除账户”，但需经负责人明确认可这一可见性和隐私语义。

**审批结论**：负责人已明确批准 B，当前产品不提供已永久删除账户的恢复，也不再向用户提供包含该账户历史数据的旧全账本报告。账户删除的事务／接口／小程序影响提示属于本 S5 已批准交付的一部分；不得未经授权连接真实业务库或执行数据删除。此批准只改变业务可见性规则，不授权正式 Schema 变更；如必要，STOP 并单独审批。

**关于诊断恢复与未来数据分析**：项目负责人已明确“初期以故障排查与受控恢复为主，同时保留以后合法分析的可能性”。本 Stage 不新增历史库、全量逻辑删除改造或无期限的明文 JSON 归档，采用现有正式备份及安全边界；备份增强候选留在 Backlog，不成为本 Stage 未获批的新增交付内容。

## 4. 验收矩阵与防回归重点

1. 两个用户各自有正常／归档账户，当前用户生成报告只聚合自己所有**未永久删除**账户，不接受客户端篡改账户 id，不能穿透到另一用户。
2. 自然月 `2026-10` 和自然年 `2025` 均形成 `LEDGER` 报告；自定义起止、季度、`ACCOUNT+YEAR` 均拒绝；年报按北京时间自然年度计算，跨年日期不混入。
3. 账本中跨月转账出／入两侧业务时间不同，净值区间数据与 S4 对账；余额调整只改变余额／净值，不误计收入或支出；三级分类统计守恒、标签子树按交易 ID 去重且不把重叠标签相加。
4. 外部模型数据包仅包含必要汇总，不默认包含交易敏感备注、用户实名、内部密钥／身份 token；模型文字错误、超时和响应解析失败不能损坏已有快照。
5. 每日上限 3 次实际外部调用：重复浏览 0 次；同一用户第 4 次拒绝；跨天恢复、并发预留／释放、租约与 fencing 防重复；模拟供应商异常的扣额语义与旧功能一致。
6. 生成成功后修改历史流水：旧快照不变，重新生成必须主动触发且仍计额度；快照多版本，协调唯一键正确；单账户旧版月报仍可读，LEGACY 空账户旧行不能被误当 LEDGER。
7. 永久删除账户后的已保存 LEDGER 报告按**已批准方案 B**处理；包括删除前影响预览／事务一致性、无跨账户漏删；不得因已选择策略在未获许可的真实库执行删除。
8. 小程序展示既有月／年报告、额度状态、加载／失败／空报告及导航返回，AI 统计数字与 ST 能查证的金额一致。

## 5. 数据库、模型和安全的硬边界

- **V18 已审批并在专用隔离库演练通过，不等于任意环境可自动迁移**。尤其禁止因 Spring／Flyway 默认配置而把 V18 运行在 `bookkeeping`、`bookkeeping_test`、共享或真实业务库；测试前审查配置与库身份，并使用已授权隔离非真实数据环境和可验证的恢复点。
- 当实际集成测试必须连接 MySQL 时，先做库名、数据性质、备份与恢复脚本检查；若不能确认合法目标，**STOP 数据库相关测试**，不得因省事修改默认环境或“先跑再说”。独立 Gate 应如实记为未测，不得写 PASS。
- 不修改已执行的 V1～V18；必要正式 Schema 新增、未获批历史迁移、数据库授权拓展、真实敏感数据读写均需负责人另行明确批准。
- 不新增 Redis、MQ、AI 基础设施、新模型供应商或未经批准的按量付费外部动作。优先复用已有模型调用封装与已批准成本控制。测试优先使用 Stub／合成财务数据；真实外部调用必须符合现有模型配置、数据处理边界及额度约束。
- 错误与输出按 P0～P3 分级：跨用户、不可逆丢账务事实、超额实际模型调用或严重错账属阻断；非阻断 UI 文案留正式 Backlog。
- 不把系统恢复用的临时归档与未来分析价值未经批准塞进本 Stage，不以非功能平台建设拖慢 AI-01～07。
