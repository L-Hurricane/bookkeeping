# S6 UAT-03 单账户逐笔交易后余额｜源码评估

状态：只读评估。负责人尚未决定延期或实现。本次没有编码逐笔余额，也没有新增 Schema。

逐笔余额的定义：某一账户上，一笔记录在该账户自己的业务时间顺序中生效之后的历史账面值。转账两侧各自用自己的业务时间。余额调整只用已保存的调整额，不从历史目标余额回推。同一秒按正式流水顺序。已保存的未来业务时间立刻改变当前账面余额，但在历史序列里仍落在它的业务时间。修改历史后可以重算其后的展示余额，不能改写已保存的调整额。

## 现有源码

- 单账户月流水是 `LedgerService.query`，`GET /api/v1/accounts/{accountId}/ledger?month=YYYY-MM`。它把交易、余额调整和转账合成一个月，整月返回，没有游标。排序是 `LedgerOrdering.LEDGER`：`business_time DESC, first_save_order DESC, first_saved_at_utc DESC, kind DESC, id DESC`。
- 响应里的 `currentBalance` 来自 `CurrentBalance.of`。这是当前账面余额，包含已保存的未来业务时间，不是某一笔之后的历史余额，也不是月末余额。
- 转账在同一条 SQL 里按方向取时间：转出用 `from_business_time` 和负金额，转入用 `to_business_time` 和正金额。
- 余额调整读取已保存的 `adjustment_amount`，不重算。
- `CurrentBalance.asOf(accountId, cutoff)` 用 `business_time <= cutoff` 汇总该账户。转出、转入分别用各自的业务时间。它精确到秒，不区分同一秒里的先后。同一秒的两笔不能靠再调一次 `asOf` 分开。
- 本次为全部交易增加的 `GET /api/v1/ledger` 是只读分页。它沿用同一排序，并在转账两侧都可能出现时追加 `account_id`。响应没有逐笔余额。
- 统计 `NetWorth.closing` 是区间期末，按日截止到 23:59:59。它可以表示一个账户某月的月末，或本月截至今天结束。它不是逐笔余额。

## 三条路径

### 1. 复用现有余额服务，不改 Schema

不能把 `currentBalance` 填到每一行，也不能在客户端用当前余额倒推。对每一行调用 `asOf` 会变成逐笔全历史查询，本次明确不做。

可行的复用是：先取本页第一条之前的余额，再按正式顺序只累加这一页的有符号金额。页前余额不能只用 `asOf(该秒)`，因为同一秒里排序更前的记录会被一起算进去。页边界要按 `LedgerOrdering` 切开。

- 复杂度：中。
- Schema：不需要。
- 条件化工作量：约 3～5 人日，含转账两侧时间、固定调整额、同一秒、未来业务时间、编辑后只重算展示、以及分页边界的测试。50 行、100 行和更长历史的耗时没有测量，标为待证实。本次没有连接日常库或隔离库做计时。

### 2. 新的只读窗口

可以在路径 1 的同一次查询里用窗口累计。分页时窗口仍必须知道页前余额，不能只累计当前页却假装那就是历史余额。排序键要能分开同一秒的转账两侧。不需要新表。索引和长历史的代价待证实。复杂度和路径 1 同级，仍是中。

### 3. 持久化逐笔余额

要新增列或表，并回填。编辑、删除、改业务时间或改账户后，还要重算其后的展示值，且不能改写已保存的调整额。复杂度：高。需要单独的 Schema 批准。不建议作为这一项的做法。

## 建议

建议暂缓实现，等负责人单独确认是否纳入冻结交付范围。这不是“已经延期”的决定，也不是批准现在编码。

若之后确认要做，采用路径 1：页前一次 `asOf` 再按正式顺序累加当前页。不新增 Schema，不逐行重扫全历史，不在客户端倒推。路径 3 不采用。
