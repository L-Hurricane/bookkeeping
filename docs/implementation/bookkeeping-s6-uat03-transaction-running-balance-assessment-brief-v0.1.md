## A. 必查现有能力（用真实文件/函数/SQL 定位证据）

1. 单账户普通交易 + 转出/转入双业务时间 + 已保存固定差额余额调整是否统一组装成列表事件；排序键是否实际按业务时间、首次保存序、稳定 tie-breaker 处理。
2. 当前余额与历史时点余额算法/API，起始金额、已保存未来交易立即影响当前余额、历史时点必须按业务时间截止的区别；是否已有按时间点/账户批量计算的能力。
3. 现有单账户流水分页接口与查询索引，是否支持稳定游标和包含转账两侧及余额调整；任何逐笔查询不可用 N+1 历史余额独立调用凑数。
4. 需要正确覆盖的场景：同秒多笔交易、含负金额的收入/支出、补录早于账户创建、历史编辑/删改、跨月双时点转账、固定差额余额调整、负信用余额、未来时间业务记录、归档账户只读。
5. 用已授权隔离合成数据做**必要的只读性能测量**：典型 50/100 条分页和较长历史的范围；若需要构造新合成数据，只允许在既有授权隔离库与可恢复条件下操作，不能迁移日常/真实库、不能调用外部付费模型。

## B. 评估交付（一次简报，不增 Gate）

- 路径 1：现有查询/余额服务是否能批量复用，且无需正式 Schema；最小改动文件与接口契约、复杂度/人日级粗估、验证项。
- 路径 2：需要新增只读聚合查询或窗口/区间计算，是否触发索引/性能隐患；成本与风险。
- 路径 3：需要新持久化余额快照或正式 Schema/大量回填等高风险工作；清晰说明为什么应延期及所需审批。
- 给出推荐：**本轮纳入（须负责人额外确认冻结交付范围）/明确延期**，理由必须来自真实源码和足够的性能证据。

## C. 严格业务定义

逐笔余额为**按该账户自身业务时间顺序、在该事件生效之后的历史账面值**；转账两侧各在自己的业务时间生效；余额调整使用提交时固定的差额，绝不能重新按历史时点目标余额回填；同秒稳定排序按正式交易排序规则。已保存未来业务记录虽立即影响“当前账面余额”，仍须按其业务时间进入逐笔历史顺序。改历史数据时后续显示余额可重新推导，而非偷偷覆写既有固定调整事实。

**禁止**：为每条流水单独查一次全量历史、前端倒推每笔余额、为性能先建未批 Schema/Redis/历史快照、使用真实业务数据、将调查视为 S6 Coding 授权。无足够证据如实标明不确定性。
